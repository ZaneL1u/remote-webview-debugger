# Протокол RWD (v1)

Это контракт между шлюзом ([`gateway/`](../gateway)), SDK страницы ([`sdk/`](../sdk), его движок — в [`packages/chobitsu/src/engine/`](../packages/chobitsu/src/engine)), веб-консолью ([`console/`](../console)) и MCP-клиентами. Когда протокол меняется, первым меняется этот документ.

Общую картину (компоненты, модель согласия, хранение данных, безопасность) см. в [architecture.ru.md](architecture.ru.md); интеграцию в приложение — в [native-integration.ru.md](native-integration.ru.md).

Соглашения:

- **URL шлюза** — `https://<host>/v1`, например `https://rwd.example.com/v1`. Все эндпоинты находятся под ним; SDK выводит из него все адреса.
- Везде JSON. Метки времени — Unix-время в **миллисекундах**.
- `Level` — это `"observe" | "interact" | "advanced"` (см. [§6](#6-уровни-доступа)).
- Поля, не перечисленные здесь, получатель игнорирует. Новые поля всегда необязательны, поэтому старый SDK продолжает работать с новым шлюзом.

## 1. Эндпоинты

| Путь | Описание |
|---|---|
| `GET /v1/sdk.js` | SDK страницы (IIFE, который создаёт глобальный объект `RemoteWebviewDebugger`). `Cache-Control: max-age=300`, `Access-Control-Allow-Origin: *` |
| `GET /v1/sdk/<version>/sdk.js` | Тот же файл по неизменяемому URL, который зависит от содержимого (кэшируется на год; подходит для SRI). Любой другой `<version>` даёт 404. См. [§16](#16-эксплуатация) |
| `GET /v1/locales/<id>.js`, `GET /v1/sdk/<version>/locales/<id>.js` | Языковые пакеты SDK, загружаемые по требованию; `sdk.js` загружает их из того же места, где лежит сам ([§15](#15-языки)). `Cache-Control: max-age=300` |
| `GET /v1/healthz` | `{"ok":true,"version":"…","db":"sqlite"\|"postgres"}` |
| `GET /v1/metrics` | Метрики Prometheus ([§16](#16-эксплуатация)) |
| `WS /v1/page?key=<appKey>` | Соединение страницы ([§3](#3-соединение-страницы-websocket)) |
| `POST /v1/presence` | Резервный опрос, когда WebSocket не подключается ([§9](#9-резервный-опрос-присутствия)) |
| `WS /v1/devtools?ticket=<ticket>` | CDP-соединение окна DevTools, только с origin консоли ([§17](#17-devtools-для-людей)) |
| `/v1/api/…` | REST API веб-консоли ([§12](#12-rest-api-веб-консоли)) |
| `/v1/mcp` | MCP-сервер на шлюзе, Streamable HTTP, `Authorization: Bearer rwd_sk_live_…` ([§14](#14-mcp)) |
| `/demo/` | Статические файлы из `--demo-dir`, только если он задан |
| `/devtools/…` | Фронтенд Chrome DevTools, который встраивает консоль ([§17.4](#174-фронтенд)) |
| любой другой путь | Одностраничное приложение веб-консоли |

Неизвестные пути под `/v1/` возвращают `404 {"error":{"code":"not_found",…}}`. Все ответы содержат заголовки `X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`; все, кроме SDK, также содержат `X-Frame-Options: DENY`, а под `/devtools/` — `SAMEORIGIN`.

## 2. Идентификаторы

| Имя | Формат | Происхождение |
|---|---|---|
| Ключ приложения | `rwd_pk_` + 24 символа base62 | Создаётся вместе с проектом. Публичный: он виден в исходном коде страницы и позволяет только вывести страницу в сеть |
| API-ключ | `rwd_sk_live_` + 32 символа base62 | Создаётся в веб-консоли и показывается один раз. Хранится как HMAC-SHA256 с серверным секретом («перцем»). Веб-консоль показывает его первые 16 символов (`prefix`, например `rwd_sk_live_ab12`); устройства видят `"…"` и последние 4 символа префикса (`keyHint`) |
| `deviceId` | UUID v4 (принимается любое значение `[A-Za-z0-9_-]{1,64}`) | Генерируется SDK и хранится в localStorage под ключом `rwd:device` либо передаётся нативным хост-приложением через `run({ deviceId })` |
| Код устройства | `XXXX-XXXX` из алфавита `23456789ABCDEFGHJKMNPQRSTUVWXYZ` | Назначается шлюзом, когда он впервые видит `deviceId`; никогда не меняется. Когда агент подключается по нему, регистр, дефисы и пробелы не важны |
| `pageId` | 12 символов base62 (принимается любое значение `[A-Za-z0-9_-]{1,64}`) | Генерируется SDK, хранится в sessionStorage под ключом `rwd:page`: не меняется при перезагрузках и переходах в той же вкладке, новый для каждой вкладки |
| Метка страницы | `p1`, `p2`, … | Назначается шлюзом в пределах устройства; сохраняется, пока страница переподключается в течение 2-минутного льготного периода |
| Идентификатор сеанса (запуска) | Собственный идентификатор запуска хост-приложения (4–128 символов из `[A-Za-z0-9_.:-]`), иначе 16 шестнадцатеричных символов от SDK | Один запуск приложения, к которому страница относит свой журнал сеанса ([§5.4](#54-журнал-сеанса)). На шлюз отправляется только в результате `rwd.log` |
| `ref` | `e12`, `o3`, … | `eN`: элемент из последнего снимка страницы, действителен до следующего снимка этой страницы. `oN`: элемент, для которого в снимке нет узла, — оверлей или то, что перекрывает точку клика ([§5.3](#53-поведение-на-странице)); действителен, пока этот элемент есть на странице |
| Токен устройства | 64 шестнадцатеричных символа | Выдаётся один раз на `deviceId` ([§3.5](#35-токен-устройства-токен-возобновления-и-приглашения)); шлюз хранит только хеш |
| Токен возобновления | 32 шестнадцатеричных символа | Меняется при каждом `welcome` ([§3.5](#35-токен-устройства-токен-возобновления-и-приглашения)); хранится как хеш |

## 3. Соединение страницы (WebSocket)

### 3.1 Жизненный цикл

1. Страница открывает `wss://<host>/v1/page?key=<appKey>`. До апгрейда соединения шлюз проверяет:
   - ограничение частоты: 120 соединений (и вызовов presence) в минуту с одного IP клиента → `429 rate_limited`;
   - ключ приложения существует и его проект не отключён → иначе `401 bad_key`;
   - если у проекта задан `allowedOrigins`, заголовок `Origin` должен совпадать с одним из них → иначе `403 origin_not_allowed`.
2. Только текстовые фреймы, по одному JSON-объекту на фрейм. Входящие сообщения могут быть размером до 16 МиБ (скриншоты приходят в base64).
3. Страница должна отправить `hello` в течение **5 секунд**. Некорректный `hello` (битый JSON, неверный `t`, недопустимый `deviceId` / `pageId`) закрывается с кодом `1008`.
4. Шлюз отвечает `welcome` ([§3.4](#34-welcome)) или закрывает соединение с кодом закрытия протокола ([§3.6](#36-коды-закрытия)).
5. Шлюз отправляет `{"t":"hb"}` каждые **25 секунд**, а также WebSocket ping, на который нужно ответить в течение 10 секунд. SDK переподключается, если ничего не получает **60 секунд**.
6. Переподключения SDK идут с экспоненциальной задержкой от 1 до 30 с; каждая задержка выбирается случайно из верхней половины текущего шага. После **3 подряд попыток, завершившихся до `welcome`**, SDK переходит на опрос присутствия ([§9](#9-резервный-опрос-присутствия)).
7. Второе соединение с тем же `pageId` заменяет первое (оно закрывается с `1000 replaced`).
8. Отключившаяся страница сохраняет свою метку и место в течение **2-минутного льготного периода** (переходы между страницами укладываются в него с большим запасом). После этого в хронологии она становится `closed`. Два случая сокращают ожидание, чтобы пересозданный WebView не висел в списке страниц как *переподключающийся*:
   - страница, подключившаяся с **новым `pageId`**, сразу убирает все отключённые страницы с тем же URL (фрагмент `#` не учитывается);
   - отключённая страница, чей URL показывает и **подключённая** страница, убирается уже через **1,5 с**.

   В обоих случаях, если убранная страница была выбранной страницей агента, выбор переходит на живую страницу, и результат сообщает об этом ([§14.3](#143-инструменты)).
9. SDK закрывает сокет на `pagehide` (чтобы страница могла попасть в back/forward cache) и переподключается на `pageshow`.

У каждого соединения есть очередь отправки на 64 сообщения. Страница, которая не успевает её разбирать, закрывается с `1013 slow consumer`, а не замедляет шлюз.

### 3.2 Страница → шлюз

```jsonc
{"t":"hello","v":1,"sdk":"<SDK version>",
 "deviceId":"…","pageId":"…","openerId":"<pageId>"|null,
 "userId":"<string>"|null,
 "page":{"url":"…","title":"…","visibility":"visible"|"hidden"},
 "device":{"ua":"…","platform":"ios"|"android"|"web",
           "screen":{"w":393,"h":852,"dpr":3},
           "app":{"name":"…","version":"…"}|null},
 "help":false,
 "deviceToken":"<token>"|null,   // в текущих SDK присутствует всегда, см. §3.5
 "resume":"<token>"|null,        // последний токен возобновления, полученный этим pageId
 "invite":"<token>"|null}        // из ?rwd_invite=…

{"t":"page","url":"…","title":"…","visibility":"visible"|"hidden"}   // при изменении
{"t":"event","kind":"error"|"console_error"|"net_fail"|"user_tap","summary":"…","at":1730000000000}
{"t":"help","on":true}                                              // пользователь запрашивает поддержку / отменяет запрос
{"t":"control","action":"takeover"|"handback"|"end"}                // кнопки пользователя, §4
{"t":"attach_decision","requestId":"…","level":"interact"|null}     // §7
{"t":"cdp","s":"<session>"|absent,"m":"<CDP JSON>"}                 // ответ / событие DevTools, §17.2
{"id":17,"result":{…}}                                              // успешный RPC, §5
{"id":17,"error":{"code":"not_found","message":"…"}}                // ошибка RPC, §5
```

- `hello`: шлюз сохраняет `userId` (до 128 символов), `ua` (512), `platform` (16), `app`, `url` (2048) и `title` (256). `screen` — справочное поле.
- `event.summary` — одно предложение для агента, уже очищенное от замаскированных значений, например `TypeError: Cannot read properties of undefined (reading 'orderId')`, `POST /api/order → 405`, `Tapped button "Place order"`. Шлюз записывает событие любого известного вида в хронологию (до 300 байт) и игнорирует неизвестные виды. Переходы, включая внутристраничные, событиями не являются: шлюз выводит их из сообщений `page` (`navigated` в хронологии, [§12.9](#129-события-хронологии)); SDK хранит их в журнале сеанса ([§5.4](#54-журнал-сеанса)).
- SDK убирает дубликаты событий (тот же вид и summary в пределах 2 с) и отправляет не более 30 событий за 10 с. События и действия управления, возникшие без связи, ждут в очереди (до 100 сообщений) следующего `welcome`.
- `help` и `control` отправляются только по нажатиям пользователя (или по вызовам нативного хост-приложения, [§10](#10-javascript-api-для-хостов)).

### 3.3 Шлюз → страница

```jsonc
{"t":"welcome", …}                                            // §3.4
{"t":"control","state":"none"|"observe"|"agent"|"user",
 "agent":{"name":"Support Bot"}|null,"level":"interact"|null,
 "attachedMs":83000|null}                                     // §4, всем страницам устройства
{"t":"help","on":false}                                       // запрос поддержки снят: подключился агент, участник веб-консоли завершил сеанс или пользователь завершил его на устройстве
{"t":"task","task":{"title":"…","steps":["…"],"current":0,"agent":"Support Bot"}|null}  // §14.3 set_task
{"t":"attach_request", …}                                     // §7, активной странице
{"t":"attach_cancel","requestId":"…"}                         // §7, всем страницам
{"t":"devtools","s":"<session>","on":true,"by":"Ann"}         // §17.2, окно DevTools открылось / закрылось ("on":false)
{"t":"cdp","s":"<session>","m":"<CDP JSON>"}                  // §17.2, команда из этого окна
{"t":"hb"}
{"t":"reconnect","afterMs":1000}                              // зарезервировано: SDK переподключается через afterMs
{"id":17,"method":"rwd.snapshot","params":{}}                 // RPC-запрос, §5
```

SDK понимает `reconnect`; сейчас шлюз его не отправляет.

### 3.4 `welcome`

```jsonc
{"t":"welcome",
 "deviceCode":"K7Q2-9M4X",
 "label":"p1",
 "help":false,
 "control":{"state":"none","agent":null,"level":null,"attachedMs":null},
 "level":null,                       // то же, что control.level
 "resume":"<new resume token>",
 "deviceToken":"<token>",            // только если токен выдан этим welcome
 "config":{"helpButton":false,"maskSelectors":[],"maskPatterns":[],
           "confirmSelectors":[],"networkExclude":[],"sessionLog":true,
           "eruda":{"dock":false,"load":false}},   // или null, см. ниже
 "agentLang":"en",                   // язык шлюза: "en", "zh", "zh-TW", "fr"…, §15
 "task":{…}}                         // только пока подключённый агент её задал
```

`config` — удалённая конфигурация из политики проекта, чей ключ приложения использовала страница ([§11](#11-политика-проекта)). `config.helpButton` уже вычислен для `userId` этой страницы (`all` либо `listed`, и пользователь есть в списке). `config.networkExclude` добавляется к правилам, которые страница сама передала в `run({ networkExclude })` ([§10](#10-javascript-api-для-хостов)). `config.sessionLog` — переключатель журнала сеанса для проекта; `false` останавливает запись и удаляет то, что уже сохранено для этого origin ([§5.4](#54-журнал-сеанса)). `config.eruda` — политика проекта для eruda ([§11](#11-политика-проекта)); поле также может быть `null` или отсутствовать (шлюз или сохранённый `config` из времён до появления поля) — SDK читает это как `{"dock":false,"load":false}`, а собственный `run({ eruda })` страницы всё равно имеет приоритет для каждого поля по отдельности ([§10](#10-javascript-api-для-хостов)). SDK хранит последний `config` в localStorage под ключом `rwd:cfg` и применяет его на следующей странице, пока не придёт её `welcome`.

Если ответа ожидает запрос на подключение, а переподключившаяся страница — активная страница устройства, шлюз сразу после `welcome` снова отправляет `attach_request`.

### 3.5 Токен устройства, токен возобновления и приглашения

**Токен устройства.** Когда шлюз впервые видит `deviceId` от SDK, поддерживающего токены, он выдаёт токен устройства в `welcome.deviceToken` (32 случайных байта в hex; хранится только хеш). С этого момента каждая страница этого устройства должна предъявлять его в `hello.deviceToken`; если токен отсутствует или неверен, соединение закрывается с кодом **4401**. Поэтому знания `deviceId` и публичного ключа приложения недостаточно, чтобы присоединиться к чужому устройству.

- SDK хранит токен в localStorage под ключом `rwd:dtoken` и отдаёт его как `status().deviceToken`. localStorage привязан к origin, поэтому нативное хост-приложение, которое загружает несколько доменов, хранит токен у себя и передаёт его обратно через `run({ deviceToken })` ([native-integration.ru.md](native-integration.ru.md)).
- hello с полем `deviceToken` (даже `null`) считается поддерживающим токены. hello без этого поля приходит от SDK, который не умеет хранить токен; шлюз такому SDK токен не выдаёт (это заблокировало бы последующие страницы устройства), но как только у устройства появился токен, его должна предъявлять каждая страница.

**Токен возобновления.** Каждый `welcome` несёт новый токен `resume`, привязанный к `pageId`. Когда страница с известным `pageId` переподключается, её `hello.resume` должен совпадать с последним выданным, иначе соединение закрывается с кодом **4409**, и SDK начинает заново с новым `pageId`. Поэтому знания `pageId` недостаточно, чтобы выдать себя за страницу.

**Приглашение.** Когда URL страницы содержит `?rwd_invite=<token>`, SDK убирает параметр из адресной строки (`history.replaceState`), сохраняет токен в sessionStorage и отправляет его в `hello.invite`, пока не придёт `welcome`. Шлюз принимает приглашение, если оно относится к тому же проекту, не использовано и не истекло: устройство помечается как `invited` и как запрашивающее поддержку, в хронологии записывается, по какому приглашению оно пришло, а приглашение считается использованным. Недействительные приглашения молча игнорируются. См. [§12.6](#126-приглашения-устройств).

### 3.6 Коды закрытия

| Код | Значение | Реакция SDK |
|---|---|---|
| `1008` | Некорректный `hello` | Переподключение с нарастающей задержкой |
| `1013` | Страница не успевала разбирать очередь отправки | Переподключение с нарастающей задержкой |
| `4401` | Токен устройства отсутствует или неверен | Если сохранённый токен за это время изменился (другая вкладка только что его получила), сразу повторить попытку. Если токена нет вовсе, а `deviceId` собственный, сгенерированный SDK (не переданный хост-приложением), значит, welcome с токеном потерялся (первая страница ушла посреди рукопожатия): примерно через 1,5 с, если к тому времени другая вкладка не сохранила токен, начать заново с новым `deviceId` (не более двух раз на страницу). Иначе состояние `rejected` и повтор примерно через 10 минут |
| `4409` | Токен возобновления не совпадает | Новый `pageId`, переподключение |
| `4429` | Достигнута квота проекта на число устройств в сети (`maxOnlineDevices`) | Состояние `quota`, повтор примерно через 5 минут |

## 4. Состояние управления

У каждого устройства одно состояние управления; шлюз определяет его и рассылает всем страницам устройства сообщением `control`.

| Состояние | Значение | Интерфейс на странице |
|---|---|---|
| `none` | Агент не подключён | Свёрнутая плашка с кодом устройства (плюс кнопка «Запросить поддержку», если она включена) |
| `observe` | Агент подключён и только смотрит | «ИИ смотрит», ввод пользователя заблокирован (если пользователь не выключил блокировку), светящийся край экрана, кнопки **Перехватить** и **Завершить** |
| `agent` | Агент управляет страницей | «ИИ работает», та же блокировка, край и кнопки, плюс курсор агента |
| `user` | Пользователь взял управление | Без блокировки, статичный край, кнопки **Вернуть ИИ** и **Завершить** |

Переходы:

| Триггер | Изменение |
|---|---|
| Агент подключается ([§7](#7-одобрение-подключения)) | `none` → `observe` |
| Агент вызывает интерактивный инструмент (click, fill, type, press, select, hover, scroll, drag, navigate, back, reload) | `observe` → `agent`. В состоянии `user` шлюз отказывает с ошибкой `takeover`, не обращаясь к странице |
| Нет действий в течение `policy.agentIdleMinutes` (по умолчанию 2; проверка каждые 10 с) | `agent` → `observe` |
| Страница отправляет `control: takeover` | `observe` / `agent` → `user` |
| Страница отправляет `control: handback` | `user` → `agent` (или `none`, если агент не подключён) |
| Страница отправляет `control: end` | Агент отключается, запрос поддержки снимается → `none` |
| Агент отключается или заменяется, его ключ отзывается, истекает `policy.attachMaxMinutes` (по умолчанию 60) или участник веб-консоли завершает сеанс | → `none` |

Страница блокируется с момента подключения агента (`observe`), а не только когда он начинает действовать, и остаётся заблокированной при переходе `agent` → `observe` по бездействию — пока пользователь не возьмёт управление или состояние не вернётся в `none`.

`attachedMs` — сколько миллисекунд подключённый агент уже подключён на момент, когда шлюз отправил сообщение (`null`, если агента нет). Это длительность, поэтому странице не нужны часы, синхронизированные со шлюзом; нижняя панель показывает её как идущий таймер «Подключено · 01:23» в `observe`, `agent` и `user` и «Подключение…», пока у самой страницы нет связи. Если шлюз не присылает это поле, SDK отсчитывает время с момента, когда страница впервые увидела агента.

Кроме того, SDK в качестве второй проверки отклоняет интерактивные RPC с `takeover`, пока управление у пользователя. Он запоминает состояние (и момент подключения агента) на 2 минуты в localStorage под ключом `rwd:ctl`, поэтому следующая страница после перехода блокируется сразу, с идущим таймером, а не ждёт своего `welcome`. Кнопки «Перехватить», «Вернуть ИИ» и «Завершить» реагируют только на доверенные нажатия пользователя; агент не может их нажать, а нативное хост-приложение должно предъявить `nativeKey` ([§10](#10-javascript-api-для-хостов)).

## 5. RPC страницы

### 5.1 Конверт сообщения

Шлюз отправляет одной странице `{"id":<n>,"method":"rwd.…","params":{…}}`; страница отвечает `{"id":<n>,"result":{…}}` или `{"id":<n>,"error":{"code":"…","message":"…"}}`. Идентификаторы уникальны в пределах соединения. Если соединение обрывается, ожидающие вызовы сразу завершаются ошибкой.

Тайм-ауты на стороне шлюза: 20 с для MCP-вызовов, 45 с для `rwd.click`, `rwd.press` и `rwd.type` с `submit: true` (пользователя могут попросить подтвердить действие, [§8](#8-подтверждение-чувствительных-действий)), 15 с для проверки соединения из веб-консоли.

Коды ошибок:

| Код | Значение |
|---|---|
| `not_found` | Устаревший `ref` или элемент исчез, неизвестный вариант выбора, неизвестный идентификатор запроса |
| `not_interactable` | Элемент не виден, отключён, перекрыт, доступен только для чтения или не стабилизировался за 5 с |
| `timeout` | Истекло время ожидания (на странице или на шлюзе) |
| `takeover` | Управление у пользователя |
| `forbidden` | Выше выданного уровня ([§6](#6-уровни-доступа)) или пользователь отклонил подтверждение |
| `bad_request` | Отсутствующий или недопустимый параметр, неизвестный метод |
| `internal` | Всё остальное (сообщение содержит ошибку JavaScript) |

Сообщения, которые пишет SDK, выводятся на языке агента (`welcome.agentLang`, [§15](#15-языки)).

### 5.2 Методы

Каждый метод действует на той странице, которая его получила.

| Метод | Уровень | params | result |
|---|---|---|---|
| `rwd.ping` | observe | `{}` | `{"at":<ms>}` |
| `rwd.snapshot` | observe | `{}` | `{"url","title","snapshot"}`: снимок доступности в AI-формате Playwright (YAML, элементы помечены `[ref=eN]`), а за ним — раздел оверлеев, если что-то парит над страницей ([§5.3](#53-поведение-на-странице)) |
| `rwd.query` | observe | `{"text"?,"role"?,"name"?,"limit"?:20}` (хотя бы один критерий; `limit` 1–100) | `{"matches":[{"ref","role","name","text"}],"total"}` |
| `rwd.screenshot` | observe | `{"format"?:"jpeg"\|"png"\|"webp","quality"?:80,"fullPage"?:false,"ref"?}` | `{"data":"<base64>","mimeType","source":"native"\|"dom","width","height"}` |
| `rwd.console` | observe | `{"sinceId"?,"limit"?:100,"types"?:["error","warn"]}` | `{"messages":[{"id","type","text","at","source"?}],"dropped"}` |
| `rwd.network` | observe | `{"sinceId"?,"limit"?:100,"failedOnly"?:false,"exclude"?:[],"includeExcluded"?:false}` | `{"requests":[{"id","method","url","status","type","durationMs","size","error"?,"at"}],"dropped","hidden"}` |
| `rwd.waitFor` | observe | `{"text"?,"textGone"?,"timeMs"?,"timeoutMs"?:10000}` | `{}` |
| `rwd.log` | observe | `{"op":"sessions"\|"overview"\|"records", …}`, см. [§5.4](#54-журнал-сеанса) | Зависит от `op` |
| `rwd.click` | interact | `{"ref","button"?:"left","clickCount"?:1}` | `{}` |
| `rwd.hover` | interact | `{"ref"}` | `{}` |
| `rwd.fill` | interact | `{"ref","value"}` | `{}` |
| `rwd.type` | interact | `{"text","ref"?,"submit"?:false}` | `{}` |
| `rwd.press` | interact | `{"key"}`: имена клавиш Playwright, сочетания вроде `Control+A` | `{}` |
| `rwd.select` | interact | `{"ref","values":["…"]}` | `{"selected":["…"]}` |
| `rwd.scroll` | interact | `{"ref"?,"dx"?:0,"dy"?:0}` | `{}` |
| `rwd.drag` | interact | `{"fromRef","toRef"}` | `{}` |
| `rwd.navigate` | interact | `{"url"}` | `{}` (затем страница переподключается) |
| `rwd.back` / `rwd.reload` | interact | `{}` | `{}` |
| `rwd.evaluate` | advanced | `{"function":"() => …","args"?:[]}` | `{"value":<JSON>}` |
| `rwd.networkDetail` | advanced | `{"id"}` | `{"request":{"headers","body"?},"response":{"headers","body"?}}` |
| `rwd.storage` | advanced | `{"area":"local"\|"session"\|"cookie"}` | `{"entries":[{"key","value"}]}` |
| `rwd.logDetail` | advanced | `{"seq"}` | Одна запись журнала сеанса целиком: `{"seq","session","at","kind","page","imp","size","data"}`, включая заголовки и тела ([§5.4](#54-журнал-сеанса)) |

Подробности:

- `rwd.query` сопоставляет `role` точно (без учёта регистра), а `name` / `text` — как подстроки без учёта регистра; `text` охватывает собственный текст элемента и текст его потомков, и возвращается только самое внутреннее совпадение.
- `rwd.fill` работает с текстовыми полями, textarea и элементами `contenteditable` (`<label>` перенаправляется на связанный с ним элемент управления). Он задаёт значение через нативный сеттер и отправляет события `input` и `change`, поэтому контролируемые поля React и Vue видят изменение. Для `<select>` нужен `rwd.select`.
- `rwd.type` фокусирует `ref` (курсор в конце), если он задан, иначе вводит текст в элемент с фокусом; `submit: true` затем нажимает Enter.
- `rwd.select` сопоставляет каждое значение со значением, меткой или текстом варианта. Для нескольких значений нужен select с атрибутом `multiple`.
- `rwd.scroll` без `ref` прокручивает страницу; с `ref` он отправляет событие wheel на элемент и прокручивает его прокручиваемого предка. Прокрутка анимируется примерно 0,3 с, чтобы пользователь успевал за ней следить.
- `rwd.navigate` принимает только абсолютные или относительные URL `http(s)`. Переход, возврат назад и перезагрузка выполняются через 50 мс после отправки ответа.
- `rwd.waitFor` сначала ждёт `timeMs` (не более 60 с), затем каждые 100 мс опрашивает видимый текст (`document.body.innerText`), пока не появится `text` и не исчезнет `textGone`, или завершается с `timeout` по истечении `timeoutMs`.
- `rwd.screenshot` использует нативный захват экрана хост-приложения, если он зарегистрирован и область находится внутри viewport (`source: "native"`), иначе заново отрисовывает DOM (`source: "dom"`; canvas, видео и изображения с других origin могут оказаться пустыми). `ref` обрезает снимок по элементу; `fullPage` захватывает весь документ. См. [§10](#10-javascript-api-для-хостов).
- `rwd.console` / `rwd.network` с `sinceId` возвращают `limit` самых старых записей после него; без него — `limit` последних. У запросов, которые ещё выполняются, `status: 0` и `durationMs: null`; `type` — это `xhr`, `fetch`, `websocket`, `beacon` или `eventsource`.
- `rwd.network` не включает запросы, совпавшие с правилами исключения — `networkExclude` проекта плюс `run({ networkExclude })` ([§11](#11-политика-проекта)), плюс `exclude` только для этого вызова, — а `hidden` их подсчитывает. `includeExcluded: true` возвращает все запросы и оставляет `hidden` равным 0. Исключённые запросы всё равно записываются, и `rwd.networkDetail` по-прежнему возвращает их по идентификатору.
- `rwd.networkDetail` скрывает заголовки `Cookie`, `Set-Cookie`, `Authorization` и `Proxy-Authorization`; тела маскируются и обрезаются до 64 КБ.
- `rwd.storage` возвращает не более 500 записей, значения обрезаются до 4000 символов. Cookie — только те, что доступны скриптам (не HttpOnly). Собственные `rwd:dtoken` и `rwd:resume` SDK всегда маскируются.
- `rwd.evaluate` вычисляет исходный код функции в глобальной области видимости страницы и вызывает её с `this = window`; функция может вернуть промис. Результат приводится к безопасному для JSON виду: `undefined` и функции становятся `null`, элементы — кратким описанием тега, даты — строками ISO, циклические ссылки — `"[Circular]"`.

### 5.3 Поведение на странице

- **Готовность к действию.** Действия указателем ждут (до 5 с), пока элемент не будет присоединён к документу, видим, стабилен в течение двух кадров анимации, включён и прокручен в область видимости, а проверка попадания (hit test) в целевой точке не попадёт в сам элемент или его потомка. Первой пробуется видимая середина элемента — туда нажал бы палец; если её что-то перекрывает, пробуются остальные точки сетки 3×3 внутри видимой области элемента, так что значок поверх кнопки не мешает клику. Если перекрыты все точки, вызов завершается с `not_interactable` и сообщением, которое называет перекрывающий элемент и его `ref` (*the click point is covered by `<div.popup-mask>` (ref=o1; click it directly…)*), — агент может кликнуть по нему. Проверка попадания пропускает собственный интерфейс SDK и другие инструменты отладки (`.__chobitsu-hide__`, `#eruda`, `#__pageSpy`, `#__vconsole`).
- **Оверлеи.** Снимок заканчивается разделом `[Overlays]`, когда над страницей парят слои: фон всплывающего окна, модальное окно, нижний лист (bottom sheet). Они находятся проверкой попадания в нескольких точках viewport: остаётся то, что лежит в фиксированном блоке (или в абсолютном блоке размером с viewport), который закрывает не менее 15% viewport и сам не содержит половину элементов снимка (это был бы корень самого приложения, а не слой над ним). В каждой строке — тег элемента, несколько слов его (очищенного) текста, доля закрытого им viewport и `ref`; слой без текста и медиа указывается как фон (backdrop). У пустого фона нет узла в aria-снимке, поэтому он получает ref вида `oN` — именно это позволяет агенту нажать на фон, чтобы закрыть всплывающее окно.
- **Синтетический ввод.** Клик отправляет `pointerover/enter → pointerdown → mousedown → focus → pointerup → mouseup → click`, а на сенсорных устройствах — ещё и touch-события. У этих событий `isTrusted: false`; страницы, которые это проверяют, на них не отреагируют.
- **Обратная связь.** Цель ненадолго подсвечивается, и курсор агента на странице перемещается к ней до отправки ввода.
- **Маскирование.** Значения `input[type=password]`, элементов с `data-rwd-mask` и `maskSelectors` проекта заменяются на `••••` в снимках и скриншотах (на нативных скриншотах поверх них рисуются серые прямоугольники). Эти значения, а также текст, совпадающий с `maskPatterns`, заменяются и в тексте console, URL и телах сетевых запросов, значениях хранилища и summary событий.
- **Область снимка.** Корень снимка — `<body>`. Интерфейс SDK живёт в Shadow DOM под `<html>`, вне `<body>`; узлы eruda, PageSpy и vConsole удаляются из снимка.
- **Буферы.** Console, необработанные ошибки и сеть (XHR, fetch, WebSocket, sendBeacon, EventSource) записываются с момента загрузки SDK в кольцевые буферы по 500 записей каждый. При заполнении первыми отбрасываются обычные логи и успешные запросы; `dropped` их подсчитывает. Тела ответов кэшируются в пределах 5 МБ в сумме и 64 КБ на каждое.

### 5.4 Журнал сеанса

Буферы из [§5.3](#53-поведение-на-странице) живут в памяти одной страницы. **Журнал сеанса** — их длинная версия: всё, что произошло на этом origin с момента запуска приложения, записанное в **IndexedDB** (база данных `rwd-log`) каждой страницей этого origin, независимо от того, доступен ли шлюз. Поэтому агент, подключившийся постфактум, может прочитать весь путь к ошибке через перезагрузки и разные страницы. Журнал никогда не покидает устройство, если его не запросит подключённый агент.

**Сеанс — это один запуск приложения.** Идентификатор определяется в таком порядке:

1. `run({ launchId })` — собственный идентификатор запуска хост-приложения, который генерируется при каждом холодном старте и одинаков для всех WebView этого процесса;
2. `window.RWDLaunchId`, который может определить хост-приложение или фрагмент кода интеграции: строка или функция, возвращающая строку (или промис строки, его ждут не более 300 мс);
3. выводится SDK: сеансовая cookie `rwd_launch` (без срока действия, поэтому она умирает вместе с процессом приложения) плюс heartbeat каждые 10 с. Cookie-сеанс, молчавший больше **1 часа**, считается более ранним запуском, и начинается новый идентификатор — так обрабатываются WebView, которые сохраняют сеансовые cookie между запусками.

`source` сеанса показывает, какой вариант сработал: `app` для 1 и 2, `cookie` для 3.

**Что записывается.** У каждой записи есть `seq` (ключ, возрастает), `at`, `kind`, `page` (`pageId` записавшей страницы) и `data`:

| `kind` | `data` |
|---|---|
| `page` | `event: "open"` (url, title, referrer), `"nav"` (from, url, title — включая внутристраничные переходы), `"visibility"` (передний план / фон), `"hide"` (страница ушла) |
| `action` | Собственный (доверенный) ввод пользователя: `"tap"` (описание элемента), `"input"` (описание поля и значение), `"submit"`, `"scroll"` (где остановилась прокрутка). Значение поля пароля, элемента с `data-rwd-mask` или элемента, совпавшего с `maskSelectors`, хранится как `••••`, никогда в открытом виде; остальные значения очищаются по `maskPatterns` и обрезаются до 200 символов |
| `agent` | Интерактивные вызовы агента и `rwd.evaluate`: метод, `ref`, клавиша, url, значения, текст и ошибка, если вызов не удался. Чтения (снимки, списки) не записываются |
| `control` | Изменения состояния управления с именем агента ([§4](#4-состояние-управления)) |
| `console` | Все уровни, с `type`, `text` и `source` |
| `net` | Каждый завершённый запрос: метод, url, статус, тип, длительность, размер, ошибка. **Неудачный** запрос также содержит `reqHeaders` / `resHeaders` (скрытые так же, как в `rwd.networkDetail`) и `reqBody` / `resBody`, каждое обрезано до 64 КБ |

Ошибки и предупреждения console, неудачные запросы, нажатия, ввод и отправки форм пользователем, действия агента и изменения управления помечаются как важные и хранятся дольше всего. *Проблемы*, которые выбирают `problems` и `overview`, — это ошибки console и неудачные запросы.

**Ограничения.** Хранятся последние **3** запуска, каждый в пределах **10 МБ**. При превышении сначала отбрасываются самые старые неважные записи (обычные логи console, успешные запросы), затем самые старые из всех, пока объём не снизится до 80% лимита; `trimmed` их подсчитывает. Если `navigator.storage.estimate()` сообщает квоту меньше 64 МБ, хранится только текущий запуск. Без IndexedDB (в некоторых приватных режимах) ничего не записывается, и `rwd.log` завершается с `internal`.

**Чтение.** `rwd.log` принимает `op`:

```jsonc
// op: "sessions" → все ещё хранящиеся запуски, новые первыми
{"sessions":[{"id","source":"app"|"cookie","startedAt","lastAt","bytes","trimmed",
              "counts":{"page","action","agent","control","console","error","net","netFail"},
              "current":true}]}

// op: "overview", params {"session"?} → один запуск в общих чертах
{"session":{…meta…,"current":true},"first":<ms>,"last":<ms>,
 "pages":[{"at","page","data"}],      // записи открытия страниц / переходов, последние 60
 "problems":[…records…]}              // ошибки console и неудачные запросы, последние 20

// op: "records", params {"session"?,"kinds"?:["page","action","agent","control","console","net"],
//                       "problems"?:false,"page"?:"<pageId>","text"?,"after"?:<seq>,
//                       "from"?,"to"?,"limit"?:100,"exclude"?:[],"includeExcluded"?:false}
{"session":"…","records":[{"seq","at","kind","page","data"}],
 "next":<seq>|null,                   // передайте как `after`, чтобы получить следующую порцию
 "hidden":0}                          // запросы, скрытые правилами исключения сетевых запросов (§11)
```

- `session` по умолчанию — текущий запуск (`"current"` означает то же самое); неизвестный идентификатор даёт `not_found`. Если сейчас ни один запуск не записывается, используется самый новый из сохранённых.
- `problems: true` оставляет только ошибки console и неудачные запросы. `text` — подстрока `data` записи без учёта регистра. `limit` — от 1 до 500, по умолчанию 100.
- Записи возвращаются **без** заголовков и тел; там, где тело есть, `data.hasBody` равно `true`. `rwd.logDetail` возвращает одну такую запись целиком и, как и `rwd.networkDetail`, требует `advanced` ([§6](#6-уровни-доступа)).
- Правила исключения сетевых запросов действуют и здесь: запись `net`, совпавшая с правилами, не попадает в `records` и учитывается в `hidden`, если не задан `includeExcluded`.

**Отключение.** `run({ record: false })` запрещает запись одной странице. `policy.sessionLog: false` ([§11](#11-политика-проекта)) доходит до страниц как `welcome.config.sessionLog`, останавливает запись **и удаляет журналы, уже сохранённые для этого origin**. `status().logSession` — идентификатор сеанса, в который пишет страница, или `null`, если она не записывает.

## 6. Уровни доступа

| Уровень | Разрешённые методы |
|---|---|
| `observe` | `rwd.ping`, `rwd.snapshot`, `rwd.query`, `rwd.screenshot`, `rwd.console`, `rwd.network`, `rwd.waitFor`, `rwd.log` |
| `interact` | `observe` + `rwd.click`, `rwd.fill`, `rwd.type`, `rwd.press`, `rwd.select`, `rwd.hover`, `rwd.scroll`, `rwd.drag`, `rwd.navigate`, `rwd.back`, `rwd.reload` |
| `advanced` | `interact` + `rwd.evaluate`, `rwd.networkDetail`, `rwd.storage`, `rwd.logDetail` |

Уровень подключения вычисляется так:

```
min(уровень, запрошенный агентом (по умолчанию interact),
    maxLevel API-ключа,
    maxLevel объединённой политики проектов,
    уровень, выбранный пользователем на устройстве)
```

Его проверяют обе стороны: шлюз отклоняет вызовы выше уровня (ошибка `forbidden`, запись аудита `policy.denied`), а SDK перед выполнением ещё раз сверяется с `welcome.level` / `control.level`. Неизвестные методы шлюз относит к уровню `advanced`. Если шлюз не присылает уровень, когда агент подключён, SDK считает его равным `interact`.

## 7. Одобрение подключения

Когда агент вызывает `connect_device`, шлюз объединяет политики проектов, страницы которых открыты на устройстве ([§11](#11-политика-проекта)). Если объединённое `approval` равно `prompt`, пользователь должен одобрить подключение на устройстве:

```jsonc
← {"t":"attach_request","requestId":"…",
   "agent":{"name":"Support Bot","keyHint":"…a91f"},
   "levels":["observe","interact"],   // предлагаемые уровни, ограниченные ключом и политикой; последний — тот, что запросил агент
   "expiresInSec":30,
   "purpose":"devtools"}              // только когда участник веб-консоли запрашивает DevTools (§17.1)
→ {"t":"attach_decision","requestId":"…","level":"interact"}   // или "level": null для отказа
← {"t":"attach_cancel","requestId":"…"}                         // истекло время или агент отказался от запроса
```

- Запрос отправляется **активной странице** устройства; `attach_cancel` — всем страницам.
- Отсутствие ответа в течение **30 секунд** считается тайм-аутом. MCP-вызов ждёт ответа.
- Если одному и тому же API-ключу отказали **3 раза** на одном устройстве в течение 10 минут, его запросы к этому устройству **10 минут** отклоняются без вопроса пользователю.
- На одном устройстве ответа может ожидать только один запрос.
- Диалог SDK живёт в Shadow DOM, принимает только доверенные нажатия и становится активным через 0,4 с после появления, поэтому агент не может одобрить сам себя. Вкладки одного origin делятся решением через BroadcastChannel.
- Пользователь может включить **автоматическое разрешение** с максимальным уровнем в плавающем окне SDK; тогда SDK сразу отвечает наивысшим из предложенных уровней в этих пределах и показывает уведомление. Автоматическое разрешение предназначено для агентов: запрос DevTools всегда задаётся пользователю.
- С `run({ nativeApproval: true })` SDK не показывает диалог. Вместо этого `status().pending` становится `{kind:"attach", requestId, agent:{name, keyHint}, levels, purpose, expiresAt}` (`purpose` — это `"agent"` или `"devtools"`), и нативное хост-приложение отвечает через `nativeDecide(nativeKey, requestId, level | null)`.
- После одобрения шлюз подключает агента (заменяя любого другого агента на устройстве), снимает запрос поддержки (`{"t":"help","on":false}`) и рассылает `{"t":"control","state":"observe","agent":{…},"level":"interact","attachedMs":0}`; страница сразу блокируется ([§4](#4-состояние-управления)).

При `approval: none` агент подключается сразу с вычисленным уровнем.

**Возвращение без повторного вопроса.** Агент, который сам отпускает устройство — через `disconnect_device`, подключение к другому устройству или истечение `policy.attachMaxMinutes`, — оставляет после себя разрешение: в течение **10 минут** тот же API-ключ может снова подключиться к этому устройству без диалога на телефоне, с уровнем **не выше выданного пользователем ранее** (поэтому запрос `advanced` после одобрения `observe` всё равно получит `observe`). Больше ничего не ослабляется: уровень по-прежнему ограничивают ключ, политика и собственный запрос агента, и у устройства должна быть подключённая страница. Такое подключение записывается в аудит как `attach.resume` рядом с обычным `attach.start` ([§12.7](#127-журнал-аудита)), а страница видит обычное сообщение `control`, а не `attach_request`.

Возвращение не расходует разрешение: если агент снова отпустит устройство, начнётся новое 10-минутное окно. Разрешение сбрасывается, когда сеанс заканчивается по любой другой причине: пользователь нажимает **Завершить** на устройстве, сеанс завершает участник веб-консоли (`POST /devices/:id/end`), API-ключ отзывается, к устройству подключается другой агент и заменяет этого или пользователь отклоняет запрос. Разрешение также пропадает вместе с процессом шлюза, поскольку хранится в памяти.

## 8. Подтверждение чувствительных действий

Перед действием SDK спрашивает пользователя, если агент:

- кликает (`rwd.click`) по элементу, который совпадает с `[data-rwd-confirm]` или `confirmSelectors` политики либо находится внутри такого элемента;
- нажимает Enter (`rwd.press` или `rwd.type` с `submit: true`) на таком элементе или в форме, которая его содержит (но не в textarea и не в редакторе форматированного текста).

Диалог выглядит примерно так: *ИИ хочет нажать «Оформить заказ». Разрешить?* Он принимает только доверенные нажатия и истекает через **30 секунд**. Отказ или тайм-аут завершает RPC с `{"code":"forbidden","message":"The user denied this action"}`. Одновременно может быть открыто только одно подтверждение; оно отменяется, когда пользователь берёт управление, агент уходит или соединение обрывается.

С `nativeApproval: true` `status().pending` становится `{kind:"confirm", requestId, action:'click "Place order"', expiresAt}`, и хост-приложение отвечает через `nativeDecide(nativeKey, requestId, "allow" | null)`. В `status().pending` ожидающее подтверждение имеет приоритет над ожидающим запросом на подключение.

## 9. Резервный опрос присутствия

Когда WebSocket не удаётся подключить 3 раза подряд, SDK вместо него каждые 60 секунд вызывает `POST /v1/presence`. Он отправляет `Content-Type: text/plain` с телом в JSON, поэтому предварительный CORS-запрос не нужен; шлюз отвечает с `Access-Control-Allow-Origin: *`.

```jsonc
// запрос
{"key":"rwd_pk_…","deviceId":"…","pageId":"…","page":{…},"device":{…},
 "userId":null,"help":false,"deviceToken":"…"}
// ответ
{"deviceCode":"K7Q2-9M4X","connect":false}
```

- Шлюз использует `key`, `deviceId`, `userId`, `device.{ua, platform, app}`, `deviceToken` и `help`; `pageId` и `page` — справочные. Ключ приложения и origin проверяются так же, как для WebSocket, с тем же ограничением частоты.
- Устройство, которому выдан токен устройства ([§3.5](#35-токен-устройства-токен-возобновления-и-приглашения)), должно отправлять его и здесь; иначе вызов завершается с `401 bad_token`, и данные устройства не обновляются. Устройство без токена (старый SDK) продолжает опрос без него.
- `help: true` помечает устройство как запрашивающее поддержку, так же как `hello.help`, если только агент уже не подключён.
- Опрашивающее устройство считается в сети 90 секунд после каждого вызова.
- `connect: true` сообщает странице, что WebSocket нужно открыть сейчас. Шлюз выставляет его, когда агент вызывает `connect_device` или `wait_for_device` для этого устройства.
- Для подстраховки SDK также пробует WebSocket при каждом 5-м опросе.

## 10. JavaScript API для хостов

SDK предоставляет `window.RemoteWebviewDebugger`. Страницы вызывают `run()`; нативные хост-приложения внедряют SDK и вызывают `run()` с дополнительными параметрами (см. [native-integration.ru.md](native-integration.ru.md)).

```js
RemoteWebviewDebugger.run(gatewayUrl, appKey, {
  userId,                // string | null: вошедший пользователь, его видят агенты и веб-консоль
  helpButton,            // показывать кнопку «Запросить поддержку» (объединяется через ИЛИ с helpButton политики)
  app,                   // { name, version } хост-приложения
  lang,                  // тег языка интерфейса пользователя телефона; по умолчанию из navigator.languages (§15)
  locales,               // дополнительные языковые пакеты; messages: переопределения по языкам (§15)
  theme,                 // 'auto' (по умолчанию) | 'system' | 'light' | 'dark'
  style,                 // цвета, шрифты, радиусы, z-index, положение как CSS-свойства --rwd-* (sdk/README.md)
  lockScreen,            // блокировать ввод, пока агент подключён (по умолчанию true; пользователь может изменить)
  eruda,                 // true | { dock, load, src, name }: показывать как вкладку внутри eruda
  networkExclude,        // запросы, которые не должны попадать в то, что читает агент (§11)
  record,                // вести журнал сеанса (по умолчанию true; политика может его выключить, §5.4)
  // нативные хост-приложения
  deviceId,              // один id на установку, общий для всех WebView и доменов
  deviceToken,           // токен из status().deviceToken, который хранит хост-приложение
  launchId,              // этот запуск приложения, общий для всех WebView процесса (§5.4)
  nativeKey,             // секрет, известный только хост-приложению; включает nativeControl / nativeDecide
  nativeApproval,        // хост-приложение само показывает вопросы о подключении и подтверждении
}) // → Promise<{ deviceCode, status }>
```

| Функция | Описание |
|---|---|
| `run(gatewayUrl, appKey, options?)` | Выводит страницу в сеть. Промис разрешается, как только шлюз ответил, или через 8 с с тем, что известно на этот момент. Повторный вызов возвращает тот же промис |
| `status()` | `{deviceCode, status, control, help, label, deviceId, pageId, version, lang, deviceToken, level, config, pending, logSession}`. `status` — это `idle`, `connecting`, `online`, `polling`, `rejected`, `quota` или `stopped`; `logSession` — журнал сеанса, в который пишет страница, или `null`, если она не записывает ([§5.4](#54-журнал-сеанса)) |
| `help(on = true)` | Запросить поддержку или отменить запрос |
| `setUser(userId)` | Сменить вошедшего пользователя (SDK переподключается с новым `hello`) |
| `stop()` | Отключиться и убрать интерфейс; перехват console и сети продолжается в ограниченном объёме |
| `nativeControl(nativeKey, 'takeover' \| 'handback' \| 'end')` | Собственные кнопки управления нативного хост-приложения. Возвращает `false`, если ключ не совпадает |
| `nativeDecide(nativeKey, requestId, value)` | Ответить на `status().pending`: уровень или `null` для `attach`, `'allow'` или `null` для `confirm`. Возвращает `false`, если неверны ключ, запрос или значение |

**Идентификатор запуска.** Помимо `run({ launchId })`, хост-приложение может определить `window.RWDLaunchId` до запуска SDK: строку или функцию, возвращающую строку или её промис (его ждут не более 300 мс). Значение должно состоять из 4–128 символов `[A-Za-z0-9_.:-]`; всё остальное игнорируется, и SDK определяет запуск сам ([§5.4](#54-журнал-сеанса)).

`nativeKey` записывается только во внедрённый скрипт и сравнивается за постоянное время. Скрипты страницы, включая `evaluate_script` агента, не могут его прочитать, поэтому не могут вернуть управление или одобрить сами себя.

**Нативные мосты для скриншотов.** Если хост-приложение регистрирует один из них, `rwd.screenshot` использует его, чтобы получить реальные пиксели (включая видео, canvas, изображения с других origin и нативные оверлеи). Каждый мост возвращает data URL в PNG или JPEG либо просто base64 видимой области WebView:

| Мост | Платформа |
|---|---|
| `window.RWDNativeScreenshot()` | Любое хост-приложение; возвращает `string` или `Promise<string>` |
| `webkit.messageHandlers.rwdScreenshot` | iOS / macOS `WKWebView`, регистрируется как `WKScriptMessageHandlerWithReply`; получает `{type:"screenshot"}` |
| `window.RWDAndroid.screenshot()` | Android, метод `@JavascriptInterface` |

Эталонная реализация: [`examples/mock-app/Sources/RWDMockApp/RWDNative.swift`](../examples/mock-app/Sources/RWDMockApp/RWDNative.swift).

## 11. Политика проекта

```ts
type Policy = {
  approval: 'none' | 'prompt'      // prompt: пользователь одобряет каждое подключение на устройстве (по умолчанию prompt)
  maxLevel: Level                  // наивысший уровень для этого проекта (по умолчанию interact)
  maskSelectors: string[]          // дополнительные CSS-селекторы для маскирования (помимо полей пароля и [data-rwd-mask])
  maskPatterns: { name: string; regex: string }[]  // шаблоны текста для маскирования, например номера телефонов или документов (регулярные выражения JavaScript)
  confirmSelectors: string[]       // клик по ним требует согласия пользователя (помимо [data-rwd-confirm])
  networkExclude: string[]         // запросы, которые не попадают в то, что читают агенты (§5.2)
  sessionLog: boolean              // страницы ведут журнал сеанса (по умолчанию true, §5.4)
  helpButton: 'off' | 'all' | 'listed'   // кто видит кнопку «Запросить поддержку» (по умолчанию off)
  helpUsers: string[]              // userId для helpButton = listed
  agentIdleMinutes: number         // agent → observe после такого бездействия (по умолчанию 2, максимум 120)
  attachMaxMinutes: number         // подключение завершается через это время (по умолчанию 60, максимум 1440)
  maxOnlineDevices: number         // 0 = без ограничений; сверх лимита новые устройства закрываются с 4429
  maxAgents: number                // агентов, одновременно подключённых к устройствам проекта; 0 = без ограничений
  eruda: { dock: boolean; load: boolean }  // удалённое значение по умолчанию для run({ eruda }); локальные параметры имеют приоритет для каждого поля.
                                           // В welcome.config может быть null или отсутствовать (= оба false), §3.4
  devtools: 'on' | 'off'          // администраторы могут открывать DevTools на страницах проекта из консоли (по умолчанию on, §17)
}
```

- Значения нормализуются при сохранении: `approval`, отличное от `none`, становится `prompt`, недопустимый `maxLevel` — `interact`, числа приводятся к допустимому диапазону. `maskPatterns` должны компилироваться, иначе `400 bad_policy`. Из `maskSelectors`, `confirmSelectors`, `networkExclude` и `helpUsers` удаляются пустые записи, и каждый список обрезается до 50 элементов, `maskPatterns` — до 20.
- **`networkExclude`** — это шум, через который агенту не стоит продираться: шрифты, которые всегда отдают 404, маяки аналитики. Каждое правило сопоставляется с URL запроса как подстрока без учёта регистра, как шаблон с подстановочным знаком `*` (`*/404/*`) или как регулярное выражение, если оно записано в виде `/…/` (с необязательными флагами; по умолчанию `i`). Правило, которое не компилируется, ни с чем не совпадает. Совпавшие запросы не попадают в список сетевых запросов и в события хронологии `net_fail`, но страница по-прежнему их записывает, поэтому агент может запросить их через `includeExcluded` ([§5.2](#52-методы), [§14.3](#143-инструменты)). Это удобство, а не средство защиты конфиденциальности: для данных, которые не должны покидать страницу, используйте `maskSelectors` / `maskPatterns`.
- **`sessionLog`** включён, если явно не задано `false`, в том числе для проектов, сохранённых до появления этого поля. Выключение останавливает запись на всех страницах проекта и удаляет журналы, уже сохранённые на этих устройствах для этого origin; отдельная страница может отказаться от записи сама через `run({ record: false })` ([§5.4](#54-журнал-сеанса)).
- Поля маскирования, подтверждения, исключения сетевых запросов, журнала сеанса, кнопки поддержки и eruda доходят до страниц в `welcome.config` ([§3.4](#34-welcome)); собственные правила `run({ networkExclude })` страницы добавляются к правилам проекта.
- **Несколько проектов на одном устройстве.** Устройство определяется своим `deviceId`, а не проектом: страницы, загруженные с разными ключами приложения на одном телефоне, — это страницы одного устройства. Когда агент подключается, шлюз объединяет политики проектов, чьи страницы подключены, выбирая самое строгое значение: `prompt`, если его требует хотя бы один проект, наименьшие `maxLevel`, `agentIdleMinutes` и `attachMaxMinutes` и наименьшее ненулевое `maxAgents`.

## 12. REST API веб-консоли

### 12.1 Соглашения

- Базовый путь — `/v1/api`. Вход выполняется через `POST /auth/login`; сеанс — HttpOnly cookie `rwd_session` (12 часов, `SameSite=Lax`, `Secure` при HTTPS). Учётная запись перечитывается при каждом запросе, поэтому отключение или удаление участника вступает в силу сразу.
- Каждый запрос, кроме `GET` / `HEAD`, к эндпоинту, требующему сеанса, должен содержать `X-RWD-CSRF: 1`, иначе `403 csrf`.
- Ошибки имеют вид `{"error":{"code":"…","message":"…"}}` со статусом 4xx/5xx. Сообщения выводятся на языке запроса ([§15](#15-языки)).
- Частые коды: `401 unauthorized` (вход не выполнен), `403 forbidden` (недостаточная роль), `403 csrf`, `404 not_found`, `400 bad_request`, `429 rate_limited`, `500 internal`.

Роли: `owner` (всё, включая управление участниками), `admin` (проекты, ключи, политики, устройства, приглашения, аудит), `member` (чтение проектов и устройств, проверка соединения, завершение сеансов, создание приглашений устройств, чтение журнала аудита). В таблицах ниже *member* означает любую учётную запись, выполнившую вход.

### 12.2 Учётные записи и участники

| Метод | Путь | Роль | Запрос | Ответ |
|---|---|---|---|---|
| POST | `/auth/login` | — | `{"email","password"}` | `{"ok":true}` и cookie. `401 bad_password`; `429 rate_limited` после 10 попыток в минуту с одного IP. Пустой `email` означает `admin` |
| POST | `/auth/logout` | — | — | `{"ok":true}` |

| GET | `/auth/oidc/start?redirect=/path` | — | — | `302` на поставщика единого входа с подписанным cookie `rwd_oidc` (state и верификатор PKCE, 10 минут). `404`, если единый вход не настроен |
| GET | `/auth/oidc/callback` | — | `code` и `state` от поставщика | Выполняет вход и `302` на `redirect` (путь веб-консоли, иначе `/`). При ошибке `302` на `/login?sso_error=<code>`: `provider`, `denied`, `state`, `not_allowed`, `no_account`, `disabled`, `rate_limited` |

Первый владелец создаётся при запуске из `RWD_ADMIN_EMAIL` (по умолчанию `admin`) и `RWD_ADMIN_PASSWORD` (см. [gateway/README.ru.md](../gateway/README.ru.md)). Страница веб-консоли `/invite/:token` принимает приглашение участника.

Единый вход через Feishu, Lark или поставщика OpenID Connect (`RWD_OIDC_*`, см. [gateway/README.ru.md](../gateway/README.ru.md#единый-вход)) работает наряду с паролями. Кнопка на странице входа открывает `/auth/oidc/start`; поставщик возвращает браузер на `/auth/oidc/callback`, который ставит тот же cookie `rwd_session`. Удостоверение ищется по subject поставщика; если не найдено, оно привязывается к участнику с тем же email (при этом принимается и ожидающее приглашение), а если нет и такого, получает новую учётную запись с ролью по умолчанию, если только шлюз не работает только по приглашениям. Такие учётные записи — обычные участники: владельцы меняют им роль, отключают или удаляют их, как описано выше.

### 12.4 API-ключи

API-ключи принадлежат шлюзу, а не проекту: один ключ даёт доступ ко всем устройствам.

|---|---|---|---|---|

### 12.7 Журнал аудита

`GET /audit?project=&device=<device code>&actor=&action=&from=&to=&limit=50&before=<id>` (member) → `{"events":[AuditEvent],"nextBefore":<id>|null}`, новые первыми. `limit` ≤ 200; `action` сопоставляется по префиксу (`attach.` совпадает со всеми событиями подключения); `actor` совпадает с идентификатором или именем субъекта.

| Действие | Когда |
|---|---|
| `auth.login`, `auth.login_failed` | Вход в веб-консоль |
| `member.invite`, `member.accept`, `member.sso_join`, `member.update`, `member.delete` | Управление участниками (`member.sso_join` — учётная запись, созданная при первом едином входе; у `auth.login` в этом случае есть `"method":"sso"`) |
| `project.create`, `project.update`, `project.delete`, `project.rotate_app_key` | Проекты |
| `key.create`, `key.revoke` | API-ключи |
| `invite.create`, `invite.delete`, `invite.use` | Приглашения устройств |
| `attach.request`, `attach.approve`, `attach.deny`, `attach.timeout`, `attach.resume`, `attach.start`, `attach.end` | Подключения агентов. `attach.resume` означает, что ключ вернулся в пределах льготного окна, не спрашивая снова ([§7](#7-одобрение-подключения)); `detail: {level}` |
| `rpc` | Каждый RPC страницы от агента; `detail: {method, page, latencyMs, error?}` |
| `control.takeover`, `control.handback`, `control.end` | Кнопки пользователя |
| `device.end` | Участник веб-консоли завершил сеанс |
| `policy.denied` | Вызов выше выданного уровня был отклонён |
| `devtools.request`, `devtools.approve`, `devtools.deny`, `devtools.timeout`, `devtools.open`, `devtools.close` | Окна DevTools ([§17](#17-devtools-для-людей)); у `close` есть `detail: {page, durationSec, reason}` |

События никогда не содержат содержимого страниц или значений параметров. По умолчанию они хранятся 180 дней (`RWD_AUDIT_RETENTION_DAYS`).

### 12.9 События хронологии

Каждое устройство хранит в памяти последние 300 событий хронологии; веб-консоль показывает последние 100, MCP — по умолчанию последние 50.

| `kind` | Значение |
|---|---|
| `opened` / `closed` | Страница подключилась впервые / исчезла после льготного периода ([§3.1](#31-жизненный-цикл)) |
| `navigated` / `reloaded` | Страница перешла на новый URL / переподключилась с тем же URL |
| `focus` | Страница вышла на передний план |
| `error` / `console_error` / `net_fail` / `user_tap` | События, о которых сообщила страница ([§3.2](#32-страница--шлюз)) |
| `help` | Пользователь запросил поддержку, отменил запрос или пришёл по приглашению |
| `agent` | Запросы на подключение, отказы, тайм-ауты, подключения, изменения задачи |
| `control` | Изменения состояния управления; summary называет причину (пользователь взял управление, ИИ бездействует, пользователь завершил сеанс, …) |
| `offline` | Последняя страница устройства пропала, пока был подключён агент |
| `devtools` | Запросы DevTools, одобрения и отказы, окна открыты и закрыты, одобрения отозваны ([§17](#17-devtools-для-людей)) |

## 13. Обновления в реальном времени (SSE)

`GET /v1/api/stream[?project=<id>][&lang=<tag>]` (member, аутентификация по cookie) отдаёт поток `text/event-stream`:

```
retry: 3000

event: device     data: Device                               устройство изменилось (в сети, запрос поддержки, управление, одобрение, задача…)
event: timeline   data: {"deviceId", "event": TimelineEvent}
event: ping       data: {}                                   каждые 25 с
```

Без `project` передаются события всех проектов. `EventSource` не умеет задавать заголовки, поэтому язык передаётся в `?lang=`. Медленный подписчик пропускает события, а не задерживает шлюз; веб-консоль при переподключении заново загружает данные и переходит на опрос, если поток не работает.

## 14. MCP

### 14.1 Сеансы

- Эндпоинт `/v1/mcp` (Streamable HTTP). Каждый запрос должен содержать `Authorization: Bearer <API key>`. Ключ проверяется при каждом запросе, поэтому отозванный или просроченный ключ, а также адрес вне его `ipAllowlist` сразу получают 401.
- Шлюз хранит одно состояние агента на API-ключ: подключённое устройство и выбранную страницу. MCP-сеансы с одним и тем же ключом используют его совместно. Агент подключён не более чем к одному устройству одновременно; подключение к другому устройству отключает его от первого. Ключ даёт доступ к любому устройству на шлюзе.
- Если с одним ключом больше 5 раз в минуту не удаётся найти устройство, дальнейшие поиски до конца этой минуты отклоняются — так коды устройств нельзя подобрать перебором.

### 14.2 Результаты

Каждый результат инструмента заканчивается списком того, что изменилось на устройстве с предыдущего вызова агента (не более 20 строк), поэтому агент замечает новые страницы, переходы, ошибки и перехваты управления без опроса:

```
[Session changes]
- p3 "Checkout" opened (opened by p2)
- p3 TypeError: Cannot read properties of undefined (reading 'orderId')
- The user took over
```

Содержимое, пришедшее со страницы (снимки, console, сеть, хранилище, результаты evaluate, хронология), оборачивается в тег и помечается как недоверенные данные, чтобы агент не выполнял найденные в нём инструкции.

**Режим следования.** С `follow: true` (по умолчанию) выбранная страница переключается автоматически, когда действие агента открывает новую страницу, когда пользователь выводит на передний план другую страницу или когда выбранной страницы нет уже 1,5 с; результат сообщает об этом. Выбранная страница, убранная как устаревшая ([§3.1](#31-жизненный-цикл)), заменяется страницей с тем же URL независимо от значения `follow`, поскольку старой записи больше нет.

## 15. Языки

Поддерживаемые языки: английский (`en`), упрощённый китайский (`zh`), традиционный китайский (`zh-TW`), французский (`fr`), испанский (`es`), русский (`ru`), арабский (`ar`, справа налево), японский (`ja`), корейский (`ko`), немецкий (`de`) и португальский (`pt`). Принимается любой тег BCP 47, он сводится к ближайшему языку: `en-US` → `en`; `zh-CN`, `zh_CN`, `zh-Hans` → `zh`; `zh-HK`, `zh-MO`, `zh-Hant` → `zh-TW`; `fr-CA` → `fr`; `pt-BR`, `pt-PT` → `pt`. По `Accept-Language` выбирается поддерживаемый язык с наибольшим весом.

| Аудитория | Что | Чем определяется |
|---|---|---|
| Агент | Инструкции MCP-сервера, описания инструментов и параметров, результаты инструментов, `[Session changes]`, ошибки | `RWD_LANG` / `--lang` шлюза (по умолчанию `en`) |
| Агент, со стороны страницы | Сообщения об ошибках RPC и summary событий, которые пишет SDK | `welcome.agentLang`, который несёт язык шлюза. SDK хранит последнее значение в localStorage под ключом `rwd:alang` для событий, возникших до следующего `welcome`, и использует английский, пока не узнает другое |
| Веб-консоль | Сообщения об ошибках, summary хронологии и системные метки в ответах REST и SSE | `?lang=` в запросе, затем `Accept-Language`, затем язык шлюза |
| Пользователь телефона | Плашка, панели, диалоги и уведомления SDK | `run({ lang })`, иначе первый из `navigator.languages`, для которого у SDK есть пакет (встроенный или зарегистрированный страницей), иначе английский. Пакеты, кроме `en` и `zh`, загружаются по требованию из `locales/<id>.js` рядом с `sdk.js` или со шлюза (`/v1/locales/<id>.js`) |

Поэтому китайскоязычный пользователь может работать с англоязычным агентом: диалог говорит *AI 想要点击「提交订单」，允许吗？*, а при отказе агент читает *The user denied this action*.

## 16. Эксплуатация

- **Метрики.** `GET /v1/metrics` возвращает текст в формате Prometheus. Если задан `RWD_METRICS_TOKEN`, требуется `Authorization: Bearer <token>`. Серии: `rwd_online_devices{project}`, `rwd_connected_pages`, `rwd_attached_agents`, `rwd_ws_connections`, `rwd_rpc_total{method,result}`, `rwd_rpc_duration_seconds{method}` (гистограмма), `rwd_http_requests_total{code}`.
- **Версии SDK.** Версия SDK для кэширования — первые 12 шестнадцатеричных символов SHA-256 от встроенного в шлюз `sdk.js`, поэтому `/v1/sdk/<version>/sdk.js` меняется всякий раз, когда меняется файл. `GET /v1/api/config` возвращает её как `sdkVersion` вместе с `sdkIntegrity` (`sha384-…`, для атрибута `integrity`). Веб-консоль предлагает фрагмент кода, закрепляющий эту версию.
- **База данных.** `RWD_DATABASE_URL=postgres://…` (или `postgresql://`) выбирает Postgres; иначе `RWD_DATA` (по умолчанию `rwd.db`) — файл SQLite. Схема создаётся и мигрируется при запуске.
- **Ограничения частоты.** Вход в веб-консоль и принятие приглашений: 10 в минуту с одного IP клиента. Соединения страниц и вызовы presence: 120 в минуту с одного IP клиента. IP клиента берутся из `X-Forwarded-For` только с `--trust-proxy`; тот же переключатель управляет `X-Forwarded-Proto` и `X-Forwarded-Host`, от которых зависят флаг `Secure` у cookie сеанса, а также схема и хост выводимого `gatewayUrl`, когда `--public-url` не задан.
- **Хранение аудита.** `RWD_AUDIT_RETENTION_DAYS` (по умолчанию 180); старые события удаляются каждые 6 часов.

Все настройки шлюза перечислены в [gateway/README.ru.md](../gateway/README.ru.md).

## 17. DevTools для людей

Владельцы и администраторы могут открыть **Chrome DevTools** на любой подключённой странице устройства из консоли: Elements (стили, box model, подсветка на устройстве), Console (в реальном времени, с просмотром объектов и выполнением скриптов), Network (с телами ответов) и хранилище Application. Это настоящий фронтенд DevTools — собранный заранее в [chii](https://github.com/liriliri/chii); бэкенд — это уже имеющийся в SDK страницы полный chobitsu, а сообщения CDP передаёт шлюз.

```
Console /devices/:id/devtools
  └─ iframe /devtools/chii_app.html?ws(s)=<host>/v1/devtools?ticket=…   ← DevTools frontend
        │ CDP (WebSocket)
        ▼
Gateway /v1/devtools ──{"t":"cdp","s","m"}──▶ page WebSocket ──▶ SDK: one session per window ──▶ chobitsu
```

### 17.1 Открытие окна

1. Консоль вызывает `POST /v1/api/devices/:id/devtools` с `{"page":"p1"}` (если не указано — страница, на которую смотрит пользователь). Только владельцы и администраторы.
2. Шлюз объединяет политики проектов, страницы которых открыты на устройстве; если хотя бы у одного `devtools: "off"`, запрос отклоняется. Если объединённое `approval` равно `prompt`, шлюз отправляет активной странице `attach_request` с `"purpose":"devtools"`, `levels: ["advanced"]` и именем участника в `agent.name`, и ждёт ответа (30 секунд; HTTP-запрос тоже ждёт). Автоматическое разрешение SDK здесь не действует. При `nativeApproval` `status().pending.purpose` равно `"devtools"` ([§7](#7-одобрение-подключения)).
3. Одобрение действует `policy.attachMaxMinutes` для этого участника на этом устройстве, поэтому перезагрузка или переход переподключаются без повторного вопроса. Если пользователь нажимает **Завершить** на устройстве или участник веб-консоли завершает сеанс (`POST /devices/:id/end`), закрываются все окна и одобрения отзываются.
4. Ответ — `{"ticket","session","page":Page,"frontendUrl"}`. `ticket` одноразовый и действителен одну минуту; `session` — идентификатор, который окно будет иметь в `Device.devtools`.
5. Фронтенд подключается к `WS /v1/devtools?ticket=…`. Подключиться может только собственный origin консоли (хост из `--public-url`, если он задан).

Коды ошибок: `device_offline`, `no_page` (страница пропала или переподключается), `busy` (устройство ждёт ответа пользователя на другой запрос), `timeout`, `denied` (403) и `forbidden` (403, отключено политикой).

### 17.2 Сообщения страницы

```jsonc
← {"t":"devtools","s":"<session>","on":true,"by":"Ann"}   // окно открылось
← {"t":"devtools","s":"<session>","on":false}              // окно закрылось
← {"t":"cdp","s":"<session>","m":"<CDP command, JSON text>"}
→ {"t":"cdp","s":"<session>","m":"<CDP answer, JSON text>"} // обратно тому окну, которое спросило
→ {"t":"cdp","m":"<CDP event, JSON text>"}                  // всем окнам этой страницы
```

- Окно относится к одному соединению страницы. Когда страница отключается (перезагрузка, переход, закрытие), шлюз закрывает её окна с кодом **4100**; консоль переоткрывает их с новым тикетом, когда страница возвращается (одобрение всё ещё действует, поэтому пользователя не спрашивают снова). Завершение сеанса закрывает их с **4403**; фронтенд, который не успевает (screencast на медленной связи), закрывается с **1013**.
- У сообщений CDP к странице своя очередь: всплеск команд от фронтенда замедляет сам этот фронтенд, а не приводит к отключению страницы как медленного получателя, поэтому RPC агентов не страдают.
- В SDK все окна делят один chobitsu, а идентификаторы команд переписываются для каждого окна отдельно. На `Runtime.enable` и `Network.enable` отвечает сам SDK, который и так собирает то и другое для агентов с момента загрузки страницы, вместе с тем, что произошло до открытия окна: сообщения console (текст замаскирован; объекты не раскрываются) и недавние запросы (тела ответов, пока они ещё кэшированы). `*.disable` любого окна не действует; когда закрывается последнее окно, SDK скрывает подсветку, останавливает screencast и освобождает объекты, которые держал для окон.
- Пока окно открыто, нижняя панель страницы показывает, что идёт отладка разработчиком, с именами участников и кнопкой **Завершить**.

### 17.3 Состояние и аудит

- `Device.devtools` перечисляет открытые окна; `Page.connected` и `Page.connectedSince` сообщают консоли, когда переоткрыть окно; `Device.pending.purpose` отмечает запрос DevTools ([§12.8](#128-типы)).
- Вид хронологии `devtools`: запросы, одобрения и отказы, окна открыты и закрыты, одобрения отозваны ([§12.9](#129-события-хронологии)).
- Действия аудита `devtools.request`, `devtools.approve`, `devtools.deny`, `devtools.timeout`, `devtools.open`, `devtools.close` ([§12.7](#127-журнал-аудита)).
- Конфиденциальность: DevTools видит страницу как она есть, и **маскирование не применяется**. Поэтому доступ ограничен владельцами и администраторами, может быть отключён для каждого проекта, спрашивает пользователя на устройстве и фиксируется в аудите.

### 17.4 Фронтенд

Фронтенд — это `public/front_end` из npm-пакета `chii` закреплённой версии, проверенный по его sha512, и копируется в `console/dist/devtools/` при сборке консоли ([`console/scripts/devtools-frontend.mjs`](../console/scripts/devtools-frontend.mjs)). Шлюз встраивает его в сжатом виде (около 3,4 МБ) и отдаёт с `Content-Encoding: gzip`; ответы под `/devtools/` несут `X-Frame-Options: SAMEORIGIN`.
