02Como funciona

Três passos entre “quebrou no meu celular” e a causa raiz

  1. 01

    Adicione o SDK da página

    Uma tag script no <head>, o mais no início possível, para que console e rede sejam gravados desde a primeira linha. Em um app, injete o mesmo script no início do documento.

    <script src="…/npm/remote-webview-debugger">sdk.js da CDN · console + rede desde a primeira linha
  2. 02

    O usuário compartilha um código do dispositivo

    Todo celular ganha um código permanente como K7Q2-9M4X em uma pequena pílula. O usuário pode tocar em Solicitar assistência, e o dispositivo vai para o topo da lista do agente.

    K7Q2-9M4XOnlineSolicitar assistência
  3. 03

    Seu agente se conecta via MCP

    Adicione o endpoint MCP hospedado pelo gateway com uma chave de API. Depois é só descrever o problema — o agente encontra o dispositivo, pede a aprovação e começa a trabalhar.

    connect_device("K7Q2-9M4X")aprovado no celular · nível interact

03O que o agente ganha

O fluxo do DevTools, via MCP, no celular de outra pessoa

  • Snapshots de acessibilidade

    YAML no estilo do Playwright, com refs de elementos. O agente lê a página como estrutura, não como pixels — e age sobre as refs.

  • Interações reais

    click, fill, type, press, select, hover, scroll, drag — com verificação de acionabilidade e eventos que o React e o Vue aceitam.

  • Console e rede

    Gravados desde o carregamento da página em buffers limitados, então os erros de antes de o agente chegar continuam lá. Corpos sob demanda.

  • Sessões com várias páginas

    Lista → detalhe → checkout, ou uma segunda WebView: todas as páginas de um dispositivo formam uma sessão, com uma linha do tempo que atravessa as páginas.

  • Mudanças na sessão, na hora

    Todo resultado de ferramenta termina com o que mudou — página nova, navegação, um erro, o usuário assumindo o controle. Sem polling.

  • Cartão de tarefa no celular

    O agente mostra o plano e o progresso no dispositivo, para que o usuário sempre saiba o que ele está fazendo e por quê.

  • Capturas de tela

    Pixels nativos quando o app oferece uma bridge, renderização do DOM caso contrário. O mascaramento vale para as duas.

  • Log da sessão no dispositivo

    Páginas, toques, console e todas as requisições desde que o app abriu, guardados no celular no IndexedDB — e legíveis depois do fato.

  • Patches ao vivo

    No nível avançado, o agente pode aplicar um patch na página em execução com evaluate_script e verificar a correção na hora.

  • Redes ruins

    Um heartbeat leve com back-off; depois de três falhas, uma verificação de presença por minuto, e o gateway acorda a página quando for preciso.

  • 11 idiomas

    Interface do celular, console e textos para o agente em 11 idiomas, incluindo o árabe da direita para a esquerda. Traga seus próprios pacotes e a sua própria redação.

  • Qualquer cliente MCP

    Streamable HTTP em /v1/mcp para Claude Code, Codex, Cursor e companhia; uma bridge stdio minúscula para todo o resto.

04Destaques

Feito para os bugs que só acontecem lá fora

Três coisas que um cabo, uma porta de depuração remota ou uma gravação de tela não dão a você.

Log da sessão · guardado no dispositivo

O bug já aconteceu? O log ainda está no celular.

Desde o momento em que o app abre, o SDK escreve um log da sessão no IndexedDB do dispositivo: páginas visitadas, os toques e as digitações do usuário, a saída do console e todas as requisições — as que falharam com cabeçalhos e corpos. Nada é transmitido para lugar algum; o log fica no celular, sob as mesmas regras de mascaramento, até que um agente aprovado pelo usuário o peça com get_session_overview e get_session_log. As três últimas inicializações são mantidas, com até 10 MB cada.

rwd-log · inicialização 3 de 3
09:41:02 abriu index.html09:41:09 toque “Gift box”09:41:11 toque Buy now09:41:12 erro TypeError: order.price.toFixed…09:41:13 rede GET api/coupon → 40409:52:30 agente conectou (interact)09:52:31 leu get_session_log
Patch ao vivo · evaluate_script

Verifique a correção no celular do cliente, antes de publicar.

Com a aprovação avançada do usuário, evaluate_script roda dentro da página — então o agente pode corrigir um estado errado, sobrescrever uma função ou renderizar uma tela de novo e ver o resultado no aparelho de verdade: um patch ao vivo que prova o diagnóstico. Ele vive só na memória daquela página; nada é persistido, e cliques sensíveis continuam precisando do sim do usuário.

Nativo para agentes · MCP

Feito para agentes, não para uma pessoa com o DevTools aberto.

Todo resultado de ferramenta termina com o que mudou no dispositivo desde a última chamada, então o agente nunca fica fazendo polling. O conteúdo da página é entregue como dado não confiável. Um cartão de tarefa no celular mostra o plano do agente, e o gateway fala o idioma do agente — descrições e resultados das ferramentas em 11 idiomas.

05Privacidade e controle

O celular do usuário continua sendo do usuário

Depuração remota só funciona se as pessoas confiarem nela. Toda sessão é visível, aprovada e interrompível.

  • Aprovação antes de tudo

    Um agente pede para se conectar; o usuário vê quem está pedindo e escolhe um nível no celular. Só toques de verdade valem — um script não consegue se aprovar.

  • Assumir ou encerrar, quando quiser

    Enquanto o agente trabalha, a página fica bloqueada atrás de uma borda luminosa. Um toque em Assumir pausa o agente; Encerrar o desconecta.

  • Mascarado por padrão

    Senhas e tudo que estiver marcado com data-rwd-mask aparecem como •••• em snapshots, capturas de tela, console, dados de rede e no log da sessão. Adicione seletores e expressões regulares por projeto.

  • Cliques sensíveis precisam de um sim

    Marque botões com data-rwd-confirm (“Enviar pedido”, “Excluir conta”) e o usuário confirma cada clique do agente neles.

  • Níveis de permissão

    observe lê, interact opera, advanced acrescenta scripts, corpos de requisição e armazenamento. Com limite por chave e por projeto.

  • Log de auditoria

    Cada conexão, aprovação, RPC e tomada de controle é registrada com quem, o quê e quando — nunca o conteúdo da página nem os valores dos parâmetros.

  • observesnapshots, capturas de tela, console, lista de rede, log da sessão, find, wait
  • interact+ click, fill, type, press, select, hover, scroll, drag, navigate
  • advanced+ evaluate_script (patches ao vivo), corpos de requisição/resposta, armazenamento

06Apps nativos

No seu app, é um user script

Baixe o SDK uma vez e injete-o no início do documento — WKUserScript no iOS, addDocumentStartJavaScript no Android. Suas páginas web não mudam em nada.

  • Um código do dispositivo em toda parte

    Passe um deviceId estável (e guarde o deviceToken) para que o código continue o mesmo entre WebViews e domínios.

  • Controles nativos

    Mostre seus próprios botões de assumir / devolver / encerrar com nativeControl(); scripts da página não conseguem chamá-lo.

  • Diálogos de aprovação nativos

    nativeApproval: true entrega os pedidos de conexão e as confirmações para a interface do seu próprio app.

  • Capturas com pixels reais

    Uma bridge pequena (snapshot do WKWebView, bitmap no Android) dá ao agente pixels de verdade em vez de uma renderização do DOM.

RemoteDebugger.swift
import WebKit

/// Call before webView.load(…): fetch the SDK once, inject it at document start.
func installRemoteDebugger(into controller: WKUserContentController,
                           userId: String?, done: @escaping () -> Void) {
    let gateway = "https://rwd.example.com/v1"
    URLSession.shared.dataTask(with: URL(string: gateway + "/sdk.js")!) { data, _, _ in
        DispatchQueue.main.async {
            defer { done() }
            guard let data, let sdk = String(data: data, encoding: .utf8) else { return }
            let options: [String: Any] = [
                "deviceId": stableDeviceId, // a UUID kept in UserDefaults
                "userId": userId ?? NSNull(),
                "helpButton": true,
            ]
            let json = String(data: try! JSONSerialization.data(withJSONObject: options), encoding: .utf8)!
            let boot = sdk + "\n;RemoteWebviewDebugger.run(\"\(gateway)\", \"rwd_pk_…\", \(json));"
            controller.addUserScript(WKUserScript(source: boot,
                                                  injectionTime: .atDocumentStart,
                                                  forMainFrameOnly: true))
        }
    }.resume()
}
RemoteDebugger.kt
// needs androidx.webkit:webkit:1.12.0, javaScriptEnabled and domStorageEnabled
// call before webView.loadUrl(…)
fun installRemoteDebugger(webView: WebView, userId: String?, onReady: () -> Unit) = thread {
    val gateway = "https://rwd.example.com/v1"
    val sdk = runCatching { URL("$gateway/sdk.js").readText() }.getOrNull()
    webView.post {
        if (sdk != null && WebViewFeature.isFeatureSupported(WebViewFeature.DOCUMENT_START_SCRIPT)) {
            val options = JSONObject()
                .put("deviceId", stableDeviceId) // a UUID kept in SharedPreferences
                .put("userId", userId ?: JSONObject.NULL)
                .put("helpButton", true)
            val boot = "$sdk\n;RemoteWebviewDebugger.run(${JSONObject.quote(gateway)}, \"rwd_pk_…\", $options);"
            WebViewCompat.addDocumentStartJavaScript(webView, boot, setOf("https://m.example.com"))
        }
        onReady()
    }
}

07Auto-hospedado

Um binário Go. Seus servidores. Seus dados.

O gateway embute o console web e o SDK da página. SQLite de fábrica, Postgres quando você precisar, Docker Compose e Caddy para o HTTPS.

  • Console

    Dispositivos, chaves de API, membros e papéis, convites por QR code, políticas e um log de auditoria — além de um guia de integração já preenchido com as suas chaves.

  • Armazenamento

    Arquivo SQLite por padrão; defina RWD_DATABASE_URL=postgres://… para usar Postgres.

  • Operação

    Métricas do Prometheus em /v1/metrics, URLs do SDK versionadas com SRI, health check em /v1/healthz.

08Perguntas frequentes

O que as pessoas perguntam

O usuário precisa instalar alguma coisa?

Não. Em páginas H5, o SDK faz parte da sua página. Em um app, você o injeta pelo código nativo. O usuário só vê uma pequena pílula com o código do dispositivo e, quando um agente se conecta, um diálogo de aprovação.

O que o agente consegue ver e fazer?

Só o que o usuário aprovou: as páginas WebView daquele dispositivo, no nível concedido. Ele nunca controla nada fora da WebView. Campos mascarados continuam mascarados, e o conteúdo da página é passado ao modelo como dado não confiável.

O bug aconteceu antes de o agente se conectar. Está perdido?

Não. O SDK mantém um log da sessão no dispositivo desde que o app abriu — páginas, toques, console e requisições — então um agente que se conecta depois lê todo o caminho até o bug com get_session_log. Fora isso, o log nunca sai do celular.

O agente consegue corrigir o bug no celular?

Ele consegue verificar uma correção: no nível advanced, evaluate_script aplica um patch na página em execução, em memória — corrigir um estado, sobrescrever uma função, renderizar de novo — e o agente vê se o problema desaparece. A correção de verdade continua indo pelo seu processo de release normal; nada é persistido no dispositivo.

Com quais agentes funciona?

Com qualquer cliente MCP. O Claude Code, o Codex e o Cursor usam direto o endpoint Streamable HTTP hospedado; clientes que só falam stdio usam rwd mcp, uma bridge pequena para o mesmo endpoint.

Quais plataformas são suportadas?

Qualquer WebView ou navegador móvel moderno: WKWebView no iOS, Android System WebView, navegadores dentro de apps e o Safari ou o Chrome do celular. Navegadores de desktop também funcionam.

E em redes ruins ou com o WebSocket bloqueado?

A página mantém um WebSocket de heartbeat leve com back-off exponencial. Se ela não conseguir se conectar três vezes seguidas, passa a uma verificação de presença por minuto, e o gateway a acorda quando um agente quiser se conectar.

Isso deixa a minha página mais lenta?

É uma tag script. Os registros de console e de rede ficam em ring buffers limitados (500 entradas cada, corpos de resposta limitados a 5 MB), o log da sessão é escrito em segundo plano e uma conexão ociosa só troca heartbeats.

Funciona junto com eruda, vConsole ou PageSpy?

Sim — os nós deles são ignorados pelos snapshots e pelo hit-testing, o nosso próprio tráfego fica fora dos logs de rede deles, e ele pode até viver como uma aba dentro do eruda.

A demo acima é real?

O SDK é real e sem modificações; só o gateway é simulado no seu navegador. Um shim de WebSocket faz um túnel da conexão do SDK até ele com postMessage, e um agente roteirizado envia os mesmos RPCs que um gateway real enviaria. Para ver a coisa real de ponta a ponta, teste com o seu próprio agente.
