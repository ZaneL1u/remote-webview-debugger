# Шлюз rwd

Сервер Remote WebView Debugger на Go: подключения страниц, статус присутствия устройств, состояние управления, встроенный MCP-эндпоинт, REST API веб-консоли, а также встроенные в бинарник веб-консоль и SDK страницы. Весь сервер — это один бинарный файл.

- Протокол: [docs/protocol.ru.md](../docs/protocol.ru.md)
- Архитектура, модель согласия и вопросы безопасности: [docs/architecture.ru.md](../docs/architecture.ru.md)
- Развёртывание через Docker Compose: [deploy/platform/README.ru.md](../deploy/platform/README.ru.md)

## Сборка и запуск

Для сборки нужны Go (версия из `go.mod`) и Node.js с npm: веб-консоль и SDK собираются и встраиваются в бинарный файл. Из корня репозитория:

```bash
make -j16                                    # → gateway/bin/rwd-<os>-<arch>
make -j16 GOOS=linux GOARCH=amd64            # кросс-компиляция (amd64 или arm64)

RWD_ADMIN_EMAIL=you@example.com RWD_ADMIN_PASSWORD='change-me' \
  gateway/bin/rwd-darwin-arm64 serve --addr :8080
```

Откройте http://localhost:8080 и войдите с этими email и паролем. Страницы и агенты используют URL шлюза `http://localhost:8080/v1` (в продакшене — `https://rwd.example.com/v1`).

`go build ./cmd/rwd` внутри `gateway/` тоже работает, но в таком бинарнике вместо веб-консоли и SDK лежат заглушки. `make` берёт версию, которую сообщают `rwd version` и `/v1/healthz`, из последнего тега `gateway-vX.Y.Z` (`0.2.0` на самом теге, `0.2.0-3-gabc1234` после него, `0.0.0-dev`, если тегов нет); `RWD_VERSION=…` её переопределяет. Готовые бинарники для Linux и macOS (amd64, arm64) прикладываются к каждому [GitHub Release](https://github.com/ZaneL1u/remote-webview-debugger/releases) с тегом `gateway-v*`; список изменений — в [CHANGELOG](CHANGELOG.md).

## Команды

```
rwd serve [флаги]                       запустить шлюз
rwd mcp --gateway https://host/v1       stdio-мост MCP для локальных агентов (API-ключ из RWD_API_KEY)
rwd version                             вывести версию
```

## Настройка (`rwd serve`)

У каждого флага есть переменная окружения; флаг, указанный в командной строке, имеет приоритет.

| Флаг / переменная окружения | По умолчанию | Описание |
|---|---|---|
| `--addr` / `RWD_ADDR` | `:8080` | Адрес для прослушивания (обычный HTTP; TLS ставьте перед шлюзом, см. [deploy/platform](../deploy/platform/README.ru.md)) |
| `--data` / `RWD_DATABASE_URL` / `RWD_DATA` | `rwd.db` | База данных. URL вида `postgres://` или `postgresql://` выбирает Postgres; всё остальное считается путём к файлу SQLite. `RWD_DATABASE_URL` важнее `RWD_DATA`. Схема создаётся и мигрируется при запуске |
| `--public-url` / `RWD_PUBLIC_URL` | определяется по каждому запросу | Публичный URL шлюза, оканчивающийся на `/v1`, например `https://rwd.example.com/v1`. Используется во фрагментах кода для интеграции, ссылках-приглашениях и в `/v1/api/config`. Задайте его, если шлюз не может сам определить свой публичный адрес |
| `--trust-proxy` / `RWD_TRUST_PROXY=1` | выключено | Брать IP клиента из `X-Forwarded-For`, а схему и хост определяемого публичного URL (и то, ставить ли cookie веб-консоли флаг `Secure`) — из `X-Forwarded-Proto` / `X-Forwarded-Host`. Включайте только за обратным прокси, иначе клиенты смогут подделать эти заголовки и обойти списки разрешённых IP и ограничения частоты запросов. Без этого флага любой запрос считается обычным HTTP, что бы ни сообщал прокси, поэтому cookie веб-консоли ставится без `Secure`, а определяемые URL начинаются с `http://` (в этом случае задайте `--public-url`) |
| `--lang` / `RWD_LANG` | `en` | Язык всего, что читает ИИ: MCP-инструкций, описаний инструментов и параметров, результатов инструментов, `[Session changes]` и ошибок. Он также передаётся SDK страницы как `welcome.agentLang`, чтобы ошибки и сводки событий, формируемые на странице, были на том же языке. Один из `en`, `zh` (упрощённый китайский), `zh-TW` (традиционный китайский), `fr`, `es`, `ru`, `ar`, `ja`, `ko`, `de` или `pt`; региональные теги принимаются и сводятся к ближайшему (`zh-CN` → `zh`, `zh-HK` → `zh-TW`, `pt-BR` → `pt`). Веб-консоль выбирает язык для каждого запроса (`?lang=` или `Accept-Language`) и использует это значение как запасное |
| `--demo-dir` / `RWD_DEMO_DIR` | — | Раздавать этот каталог по пути `/demo/` (необязательно, для демо-страниц) |
| `--mcp-rate-limit` / `RWD_MCP_RATE_LIMIT` | `0` (без ограничения) | Сколько MCP-запросов в минуту разрешено с одного IP клиента; сверх этого возвращается `429` с `Retry-After: 60`. Предназначено для шлюза с публичным API-ключом, например для демо ([deploy/demo](../deploy/demo/README.md)). За прокси нужен `--trust-proxy`, чтобы видеть IP клиентов |
| `--demo-keys` / `RWD_DEMO_KEYS=1` | выключено | Запустить публичную демо-версию: `POST /v1/demo/keys` (без входа, CORS открыт) выдаёт каждому посетителю собственный API-ключ (уровень `interact`, действует 24 часа, не больше 5 в час с одного IP), поэтому посетители никогда не делят одного агента; а `list_devices` требует `deviceCode`, поэтому никто не может получить список чужих устройств. См. [deploy/demo](../deploy/demo/README.md) |
| `RWD_ADMIN_EMAIL` | `admin` | Email (логин) учётной записи владельца. Владелец создаётся, только пока в базе данных нет ни одного владельца (при первом запуске); если потом изменить значение, второй владелец **не** появится — оно лишь указывает, к какому владельцу относится `RWD_ADMIN_PASSWORD` |
| `RWD_ADMIN_PASSWORD` | — | Пароль владельца. Используется при создании владельца и при **каждом** последующем запуске, чтобы сбросить пароль владельца с email из `RWD_ADMIN_EMAIL`, — это заодно и способ восстановить доступ. Если этот email принадлежит не владельцу (другому участнику или никому), переменная игнорируется, а в журнале об этом сообщается со списком владельцев. Если переменная не задана и база данных пуста, генерируется случайный пароль, который один раз выводится в журнал |
| `RWD_METRICS_TOKEN` | — | Если задан, `/v1/metrics` требует `Authorization: Bearer <token>` |
| `RWD_AUDIT_RETENTION_DAYS` | `180` | Сколько дней хранить журнал аудита |
| `RWD_OIDC_*` | — | Единый вход, см. [ниже](#единый-вход) |

Что ещё полезно знать:

- Секреты, нужные шлюзу (pepper для API-ключей и секрет сеансов веб-консоли), генерируются при первом запуске и хранятся в базе данных. Делайте резервные копии базы и не выкладывайте их в открытый доступ.
- Шлюз держит живое состояние (подключённые страницы, состояние управления, хронологию) в памяти, поэтому на одну базу данных запускайте один экземпляр.
- Проверка работоспособности: `GET /v1/healthz` → `{"ok":true,"version":"…","db":"sqlite"|"postgres"}`.

## Единый вход

Участники могут входить и через Feishu, Lark или любого поставщика OpenID Connect (Keycloak, Okta, Microsoft Entra ID, Google, Authing, …); вход по email и паролю продолжает работать. Задайте поставщика и учётные данные клиента, и на странице входа появится кнопка **Войти через …**.

| Переменная окружения | По умолчанию | Описание |
|---|---|---|
| `RWD_OIDC_PROVIDER` | — | `feishu`, `lark` или `oidc`; включает единый вход. Если задан только `RWD_OIDC_ISSUER`, подразумевается `oidc` |
| `RWD_OIDC_CLIENT_ID`, `RWD_OIDC_CLIENT_SECRET` | — | Учётные данные приложения (App ID и App Secret для Feishu и Lark). Обязательны |
| `RWD_OIDC_ISSUER` | — | Issuer OpenID Connect, например `https://sso.example.com/realms/acme`; эндпоинты берутся из его `/.well-known/openid-configuration` (только `oidc`) |
| `RWD_OIDC_AUTH_URL`, `RWD_OIDC_TOKEN_URL`, `RWD_OIDC_USERINFO_URL` | эндпоинты поставщика | Переопределяют эндпоинты; для поставщика OpenID Connect без discovery задайте все три |
| `RWD_OIDC_SCOPES` | `openid profile email` (`oidc`), нет (Feishu, Lark) | Области доступа (scopes) через пробел. Для Feishu и Lark добавьте `contact:user.email:readonly` (и `contact:user.employee:readonly` для корпоративного email), чтобы у учётных записей был email |
| `RWD_OIDC_NAME` | название поставщика | Надпись на кнопке входа, например `Okta` |
| `RWD_OIDC_DEFAULT_ROLE` | `member` | Роль учётных записей, созданных при первом входе: `member` или `admin` |
| `RWD_OIDC_INVITE_ONLY=1` | выключено | Не создавать учётные записи: войти могут только существующие или приглашённые участники (с тем же email) |
| `RWD_OIDC_ALLOWED_DOMAINS` | — | Домены email через запятую, с которых разрешён вход, например `example.com` |
| `RWD_OIDC_TRUST_EMAIL=1` | выключено | Только `oidc`: доверять email поставщика, который не передаёт `email_verified` (Microsoft Entra ID). Только для однотенантного поставщика, email в котором контролирует ваша организация |
| `RWD_OIDC_SYNC_MINUTES` | `60` (Feishu, Lark) | Как часто отключать участников, покинувших организацию; `0` выключает. См. ниже |

Зарегистрируйте у поставщика этот URL перенаправления; он должен совпадать в точности: `https://<host>/v1/api/auth/oidc/callback`, то есть origin из `RWD_PUBLIC_URL` (или из запроса, если переменная не задана), за которым следует `/v1/api/auth/oidc/callback`. За прокси задайте `RWD_PUBLIC_URL`, чтобы URL не менялся.

При первом входе удостоверение присоединяется к участнику с тем же email (приглашённый участник сохраняет роль из приглашения, а приглашение расходуется) или создаёт учётную запись с ролью из `RWD_OIDC_DEFAULT_ROLE`, если не задано `RWD_OIDC_INVITE_ONLY=1`. При последующих входах учётная запись находится по subject поставщика (`open_id` для Feishu и Lark), поэтому смена email ни на что не влияет. Учётная запись, уже привязанная к другому удостоверению того же поставщика, повторно не привязывается (переназначенный почтовый ящик получает `sso_error=conflict`), а приглашение отключённого участника не трогается. Email от поставщика OpenID Connect учитывается только при `email_verified: true` (или `RWD_OIDC_TRUST_EMAIL=1`), а учётная запись без email получает логин `<provider>:<subject>`. Владельцы управляют такими участниками на странице **Участники**, как и всеми остальными: меняют роль, отключают или удаляют; отключённый участник не может войти ни одним из способов. У учётных записей, созданных единым входом, нет пароля. Шлюз получает данные пользователя от эндпоинта userinfo поставщика по только что полученному access token (authorization code flow с PKCE); ID token он не использует. Запуски входа и обратные вызовы ограничены 60 в минуту с одного IP клиента (за прокси включите `--trust-proxy`, иначе все будут делить IP прокси).

**Кто может войти.** Email от поставщика определяет, каким существующим участником станет удостоверение при первом входе, включая владельцев, поэтому тот, кто может задавать email у поставщика, может захватить эти учётные записи. Для Feishu или Lark используйте собственное приложение: войти смогут только люди из вашей организации и только с email вашей организации. Если у поставщика OpenID Connect войти может кто угодно (Google, многотенантный Entra ID), задайте `RWD_OIDC_ALLOWED_DOMAINS` или `RWD_OIDC_INVITE_ONLY=1`, иначе учётную запись получит кто угодно (при запуске в журнал пишется предупреждение); и никогда не задавайте для него `RWD_OIDC_TRUST_EMAIL=1`.

**Смена приложения или отключение единого входа.** `open_id` в Feishu и Lark принадлежат одному приложению: после перехода на другой App ID участники заново привязываются по email, а учётные записи без него (`feishu:…`) придётся удалить и пригласить снова. К тому же у учётных записей, созданных единым входом, нет пароля, поэтому при отключении единого входа владелец удаляет их и приглашает снова.

**Feishu или Lark.** На [Feishu Open Platform](https://open.feishu.cn/app) (Lark: [open.larksuite.com](https://open.larksuite.com/app)) создайте собственное приложение (企业自建应用), которым могут пользоваться только люди из вашей организации, затем:

1. Скопируйте App ID и App Secret из **Credentials & Basic Info** в `RWD_OIDC_CLIENT_ID` и `RWD_OIDC_CLIENT_SECRET`.
2. В **Security Settings → Redirect URLs** добавьте указанный выше URL перенаправления.
3. В **Permissions & Scopes** добавьте `contact:user.email:readonly` (и `contact:user.employee:readonly` для корпоративного email) и перечислите те же области доступа в `RWD_OIDC_SCOPES`. Чтобы замечать ушедших, приложению также нужны `contact:contact.base:readonly` и `contact:user.employee:readonly`, а в **Data permissions → Contacts range** должны быть все, кто входит.
4. Сделайте приложение доступным тем, кто должен входить, затем создайте и опубликуйте версию, чтобы настройки вступили в силу.

**Ушедшие сотрудники.** С Feishu или Lark шлюз каждые `RWD_OIDC_SYNC_MINUTES` минут запрашивает у Open Platform каждого участника, привязанного к приложению, и отключает тех, кто значится уволившимся или покинувшим организацию: их сеансы завершаются, их API-ключи перестают работать, их агенты отключаются, а в журнал аудита записывается `member.update` от `system` с `"reason":"left_organization"`. Затем владелец может удалить их, и это окончательно отзовёт их ключи. Учитывается только явный статус «уволен»: участник вне области контактов или неудавшийся запрос ничего не меняют (в журнал пишется, что не удалось), а последний владелец никогда не отключается. Без разрешения на контакты ничего не проверяется, и ушедший сохраняет рабочие API-ключи, пока владелец его не отключит; зато его сеанс в веб-консоли завершится в течение 12 часов, потому что войти снова он уже не может.

```bash
RWD_PUBLIC_URL=https://rwd.example.com/v1 \
RWD_OIDC_PROVIDER=feishu RWD_OIDC_CLIENT_ID=cli_a1b2c3d4 RWD_OIDC_CLIENT_SECRET='…' \
RWD_OIDC_SCOPES='contact:user.email:readonly contact:user.employee:readonly' \
  rwd serve
```

## Подключение агента

Создайте API-ключ в веб-консоли (**API keys**), затем добавьте встроенный MCP-эндпоинт в свой клиент, например в Claude Code:

```bash
claude mcp add --transport http rwd https://rwd.example.com/v1/mcp \
  --header "Authorization: Bearer rwd_sk_live_…"
```

Для клиентов, которые умеют только stdio, тот же бинарник пересылает stdio во встроенный эндпоинт:

```bash
claude mcp add rwd -e RWD_API_KEY=rwd_sk_live_… -- rwd mcp --gateway https://rwd.example.com/v1
```

| Настройка `rwd mcp` | Описание |
|---|---|
| `--gateway` / `RWD_GATEWAY` | URL шлюза, оканчивающийся на `/v1` |
| `RWD_API_KEY` | API-ключ (только через переменную окружения, чтобы он не появлялся в списке процессов) |

Один ключ даёт доступ ко всем устройствам шлюза. Инструменты перечислены в [protocol.ru.md §14](../docs/protocol.ru.md#14-mcp).

## Структура исходного кода

```
cmd/rwd/            точка входа: serve, mcp (stdio-мост), version
internal/store/     SQLite / Postgres: проекты и политики, участники, API-ключи (HMAC; уровень, срок действия,
                    список разрешённых IP), устройства и токены устройств, приглашения устройств, журнал аудита, настройки
internal/hub/       живое состояние: устройства, страницы, машина состояний управления, одобрение подключения,
                    проверки уровня, хронология, маршрутизация RPC, подписки SSE, метрики
internal/server/    HTTP: WebSocket страниц, опрос присутствия, REST со входом и ролями, MCP-инструменты,
                    SSE, /v1/metrics, статические файлы
internal/i18n/      тексты для агентов и веб-консоли на 11 языках
internal/ids/       ключи приложений, API-ключи, коды устройств, секреты
internal/web/       встроенные веб-консоль и SDK (их кладёт `make gateway`, иначе здесь заглушки)
scripts/embed.sh    кладёт console/dist и sdk.js в internal/web для go:embed
```

## Тесты

```bash
cd gateway && go test -race ./...
```

`internal/server/server_test.go` прогоняет весь сценарий с имитацией страниц и MCP-клиентом: подключение по коду устройства; одобрение на устройстве (разрешение, отказ, повторные отказы и блокировка, только просмотр); повторное подключение в пределах льготного периода без второго одобрения; проверки уровня; снимки; блокировку при первом взаимодействии; следование по страницам и отбрасывание страницы, которую заменил пересозданный WebView; перехват и возврат управления; пакетные действия; завершение сеанса пользователем; записи аудита; токены устройств (4401), токены возобновления (4409) и квоты (4429); одноразовые приглашения; срок действия ключей и списки разрешённых IP; немедленный отзыв; приглашения участников и роли; SSE и метрики; ошибки аутентификации.

Те же тесты запускаются и на Postgres (каждый тест в своей временной схеме):

```bash
RWD_TEST_DATABASE_URL='postgres://user:pw@127.0.0.1:5432/rwd?sslmode=disable' go test -race ./internal/server/
```

`make -j16 check` в корне репозитория запускает проверки шлюза, SDK и веб-консоли — те же, что и в CI.
