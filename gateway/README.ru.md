# Шлюз rwd

Сервер Remote WebView Debugger на Go: подключения страниц, статус присутствия устройств, состояние управления, встроенный MCP-эндпоинт, REST API веб-консоли, а также встроенные в бинарник веб-консоль и SDK страницы. Весь сервер — это один бинарный файл.

- Протокол: [docs/protocol.ru.md](../docs/protocol.ru.md)
- Архитектура, модель согласия и вопросы безопасности: [docs/architecture.ru.md](../docs/architecture.ru.md)
- Развёртывание через Docker Compose: [deploy/platform/README.ru.md](../deploy/platform/README.ru.md)

## Сборка и запуск

Для сборки нужны Go (версия из `go.mod`) и Node.js с npm: веб-консоль и SDK собираются и встраиваются в бинарный файл. Из корня репозитория:

```bash
make -j16                                    # → gateway/bin/rwd-<os>-<arch>
make -j16 GOOS=linux GOARCH=amd64            # кросс-компиляция (amd64 или arm64)

RWD_ADMIN_EMAIL=you@example.com RWD_ADMIN_PASSWORD='change-me' \
  gateway/bin/rwd-darwin-arm64 serve --addr :8080
```

Откройте http://localhost:8080 и войдите с этими email и паролем. Страницы и агенты используют URL шлюза `http://localhost:8080/v1` (в продакшене — `https://rwd.example.com/v1`).

`go build ./cmd/rwd` внутри `gateway/` тоже работает, но в таком бинарнике вместо веб-консоли и SDK лежат заглушки. `make` берёт версию, которую сообщают `rwd version` и `/v1/healthz`, из последнего тега `gateway-vX.Y.Z` (`0.2.0` на самом теге, `0.2.0-3-gabc1234` после него, `0.0.0-dev`, если тегов нет); `RWD_VERSION=…` её переопределяет. Готовые бинарники для Linux и macOS (amd64, arm64) прикладываются к каждому [GitHub Release](https://github.com/ZaneL1u/remote-webview-debugger/releases) с тегом `gateway-v*`; список изменений — в [CHANGELOG](CHANGELOG.md).

## Команды

```
rwd serve [флаги]                       запустить шлюз
rwd mcp --gateway https://host/v1       stdio-мост MCP для локальных агентов (API-ключ из RWD_API_KEY)
rwd version                             вывести версию
```

## Настройка (`rwd serve`)

У каждого флага есть переменная окружения; флаг, указанный в командной строке, имеет приоритет.

| Флаг / переменная окружения | По умолчанию | Описание |
|---|---|---|
| `--addr` / `RWD_ADDR` | `:8080` | Адрес для прослушивания (обычный HTTP; TLS ставьте перед шлюзом, см. [deploy/platform](../deploy/platform/README.ru.md)) |
| `--data` / `RWD_DATABASE_URL` / `RWD_DATA` | `rwd.db` | База данных. URL вида `postgres://` или `postgresql://` выбирает Postgres; всё остальное считается путём к файлу SQLite. `RWD_DATABASE_URL` важнее `RWD_DATA`. Схема создаётся и мигрируется при запуске |
| `--public-url` / `RWD_PUBLIC_URL` | определяется по каждому запросу | Публичный URL шлюза, оканчивающийся на `/v1`, например `https://rwd.example.com/v1`. Используется во фрагментах кода для интеграции, ссылках-приглашениях и в `/v1/api/config`. Задайте его, если шлюз не может сам определить свой публичный адрес |
| `--trust-proxy` / `RWD_TRUST_PROXY=1` | выключено | Брать IP клиента из `X-Forwarded-For`, а схему и хост определяемого публичного URL (и то, ставить ли cookie веб-консоли флаг `Secure`) — из `X-Forwarded-Proto` / `X-Forwarded-Host`. Включайте только за обратным прокси, иначе клиенты смогут подделать эти заголовки и обойти списки разрешённых IP и ограничения частоты запросов. Без этого флага любой запрос считается обычным HTTP, что бы ни сообщал прокси, поэтому cookie веб-консоли ставится без `Secure`, а определяемые URL начинаются с `http://` (в этом случае задайте `--public-url`) |
| `--lang` / `RWD_LANG` | `en` | Язык всего, что читает ИИ: MCP-инструкций, описаний инструментов и параметров, результатов инструментов, `[Session changes]` и ошибок. Он также передаётся SDK страницы как `welcome.agentLang`, чтобы ошибки и сводки событий, формируемые на странице, были на том же языке. `en` или `zh` (принимаются и `zh-CN`, `zh_CN` и т. п.). Веб-консоль выбирает язык для каждого запроса (`?lang=` или `Accept-Language`) и использует это значение как запасное |
| `--demo-dir` / `RWD_DEMO_DIR` | — | Раздавать этот каталог по пути `/demo/` (необязательно, для демо-страниц) |
| `RWD_ADMIN_EMAIL` | `admin` | Email (логин) учётной записи владельца. Владелец создаётся, только пока в базе данных нет ни одного владельца (при первом запуске); если потом изменить значение, второй владелец **не** появится — оно лишь указывает, к какому владельцу относится `RWD_ADMIN_PASSWORD` |
| `RWD_ADMIN_PASSWORD` | — | Пароль владельца. Используется при создании владельца и при **каждом** последующем запуске, чтобы сбросить пароль владельца с email из `RWD_ADMIN_EMAIL`, — это заодно и способ восстановить доступ. Если этот email принадлежит не владельцу (другому участнику или никому), переменная игнорируется, а в журнале об этом сообщается со списком владельцев. Если переменная не задана и база данных пуста, генерируется случайный пароль, который один раз выводится в журнал |
| `RWD_METRICS_TOKEN` | — | Если задан, `/v1/metrics` требует `Authorization: Bearer <token>` |
| `RWD_AUDIT_RETENTION_DAYS` | `180` | Сколько дней хранить журнал аудита |

Что ещё полезно знать:

- Секреты, нужные шлюзу (pepper для API-ключей и секрет сеансов веб-консоли), генерируются при первом запуске и хранятся в базе данных. Делайте резервные копии базы и не выкладывайте их в открытый доступ.
- Шлюз держит живое состояние (подключённые страницы, состояние управления, хронологию) в памяти, поэтому на одну базу данных запускайте один экземпляр.
- Проверка работоспособности: `GET /v1/healthz` → `{"ok":true,"version":"…","db":"sqlite"|"postgres"}`.

## Подключение агента

Создайте API-ключ в веб-консоли (**API keys**), затем добавьте встроенный MCP-эндпоинт в свой клиент, например в Claude Code:

```bash
claude mcp add --transport http rwd https://rwd.example.com/v1/mcp \
  --header "Authorization: Bearer rwd_sk_live_…"
```

Для клиентов, которые умеют только stdio, тот же бинарник пересылает stdio во встроенный эндпоинт:

```bash
claude mcp add rwd -e RWD_API_KEY=rwd_sk_live_… -- rwd mcp --gateway https://rwd.example.com/v1
```

| Настройка `rwd mcp` | Описание |
|---|---|
| `--gateway` / `RWD_GATEWAY` | URL шлюза, оканчивающийся на `/v1` |
| `RWD_API_KEY` | API-ключ (только через переменную окружения, чтобы он не появлялся в списке процессов) |

Один ключ даёт доступ ко всем устройствам шлюза. Инструменты перечислены в [protocol.ru.md §14](../docs/protocol.ru.md#14-mcp).

## Структура исходного кода

```
cmd/rwd/            точка входа: serve, mcp (stdio-мост), version
internal/store/     SQLite / Postgres: проекты и политики, участники, API-ключи (HMAC; уровень, срок действия,
                    список разрешённых IP), устройства и токены устройств, приглашения устройств, журнал аудита, настройки
internal/hub/       живое состояние: устройства, страницы, машина состояний управления, одобрение подключения,
                    проверки уровня, хронология, маршрутизация RPC, подписки SSE, метрики
internal/server/    HTTP: WebSocket страниц, опрос присутствия, REST со входом и ролями, MCP-инструменты,
                    SSE, /v1/metrics, статические файлы
internal/i18n/      английские и китайские тексты для агентов и веб-консоли
internal/ids/       ключи приложений, API-ключи, коды устройств, секреты
internal/web/       встроенные веб-консоль и SDK (их кладёт `make gateway`, иначе здесь заглушки)
scripts/embed.sh    кладёт console/dist и sdk.js в internal/web для go:embed
```

## Тесты

```bash
cd gateway && go test -race ./...
```

`internal/server/server_test.go` прогоняет весь сценарий с имитацией страниц и MCP-клиентом: подключение по коду устройства; одобрение на устройстве (разрешение, отказ, повторные отказы и блокировка, только просмотр); повторное подключение в пределах льготного периода без второго одобрения; проверки уровня; снимки; блокировку при первом взаимодействии; следование по страницам и отбрасывание страницы, которую заменил пересозданный WebView; перехват и возврат управления; пакетные действия; завершение сеанса пользователем; записи аудита; токены устройств (4401), токены возобновления (4409) и квоты (4429); одноразовые приглашения; срок действия ключей и списки разрешённых IP; немедленный отзыв; приглашения участников и роли; SSE и метрики; ошибки аутентификации.

Те же тесты запускаются и на Postgres (каждый тест в своей временной схеме):

```bash
RWD_TEST_DATABASE_URL='postgres://user:pw@127.0.0.1:5432/rwd?sslmode=disable' go test -race ./internal/server/
```

`make -j16 check` в корне репозитория запускает проверки шлюза, SDK и веб-консоли — те же, что и в CI.
