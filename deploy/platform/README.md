# Docker Compose deployment

Runs the gateway on a Docker host with a small [Caddy](https://caddyserver.com) in front. Two ways to expose it:

- **Behind an existing TLS proxy** (default): Caddy listens on `127.0.0.1:18788` and your nginx, Caddy, Traefik or load balancer terminates HTTPS in front of it.
- **Direct HTTPS** with `RWD_DOMAIN`: Caddy serves ports 80 and 443 itself and gets a certificate from Let's Encrypt.

`deploy.sh` builds everything locally, ships it over ssh and (re)starts the stack. Gateway settings are described in [gateway/README.md](../../gateway/README.md).

## Files

| File | Purpose |
|---|---|
| `Dockerfile` | Gateway image: Alpine plus the prebuilt `rwd` binary (console and SDK embedded). Runs as uid 10001 with `RWD_ADDR=:8080` and `RWD_DATA=/data/rwd.db`, with a health check on `/v1/healthz`. The same image is published to GHCR and also runs on its own |
| `compose.yml` | Two services. `gateway`: built from the Dockerfile, `./data` mounted at `/data`, settings from `.env`, `RWD_TRUST_PROXY=1` (only Caddy reaches it), not published. `web`: `caddy:2-alpine`, published on `${BIND:-127.0.0.1}:${PORT:-18788}`, serves `./demo` at `/demo/` and proxies everything else to the gateway |
| `Caddyfile` | Plain HTTP on `:80`. Trusts `X-Forwarded-*` only from `RWD_TRUSTED_PROXIES` (default: private ranges) |
| `compose.tls.yml` | Overlay for direct HTTPS: adds ports `443/tcp` and `443/udp` (HTTP/3), swaps in `Caddyfile.tls`, keeps certificates in the `caddy-data` volume |
| `Caddyfile.tls` | Serves `RWD_DOMAIN` over HTTPS with an automatic certificate and redirects HTTP to HTTPS |
| `deploy.sh` | Build, copy, first-time `.env`, database backup, restart |

On the server, `deploy.sh` produces:

```
~/rwd-platform/
├── .env                      settings (mode 600; created on the first deploy, then left alone)
├── Dockerfile  compose.yml  compose.tls.yml  Caddyfile  Caddyfile.tls
├── rwd                       the gateway binary for the server's architecture
├── data/                     rwd.db (SQLite) and rwd.db.bak-<time> backups
└── demo/platform-demo/       the demo shop, at https://rwd.example.com/demo/platform-demo/
```

## Requirements

- **Build machine:** Go, Node.js with npm, `make`, `ssh`, `scp`, `tar`.
- **Server:** Docker with the Compose plugin (`docker compose`), and `openssl`. The ssh user must be able to run Docker (for example, be in the `docker` group); no sudo is needed. The server pulls `alpine:3.22` and `caddy:2-alpine`.

## Settings (`.env`)

| Variable | Default | Description |
|---|---|---|
| `RWD_ADMIN_PASSWORD` | generated on first deploy | Owner password; **required**. Applied at every start, so changing it resets the password of the owner named by `RWD_ADMIN_EMAIL` |
| `RWD_ADMIN_EMAIL` | `admin` | Owner account (login name). Created on the first start only; changing it later does not add an owner, see [gateway/README](../../gateway/README.md) |
| `RWD_PUBLIC_URL` | derived from requests | Public gateway URL, e.g. `https://rwd.example.com/v1`. Recommended |
| `RWD_METRICS_TOKEN` | generated by `deploy.sh` | Bearer token for `/v1/metrics` |
| `RWD_DATABASE_URL` | SQLite in `./data` | `postgres://…` to use Postgres instead |
| `RWD_AUDIT_RETENTION_DAYS` | `180` | Days to keep the audit log |
| `RWD_LANG` | `en` | Language of agent-facing text: `en` or `zh` |
| `RWD_MCP_RATE_LIMIT` | — | MCP requests per client IP per minute (no limit when unset); for a public demo, see [deploy/demo](../demo/README.md) |
| `RWD_TRUSTED_PROXIES` | `private_ranges` | Address ranges (space-separated CIDRs, or Caddy's `private_ranges`) of the proxy in front of Caddy; see below |
| `BIND` | `127.0.0.1` | Address Caddy is published on |
| `PORT` | `18788` | Port Caddy is published on |
| `RWD_DOMAIN` | — | Public host name for direct HTTPS (with `compose.tls.yml` only) |
| `COMPOSE_FILE` | — | `compose.yml:compose.tls.yml` turns on direct HTTPS |

After editing `.env` on the server, apply it with `docker compose up -d` in the deployment directory.

## Deploying with `deploy.sh`

```bash
deploy/platform/deploy.sh <ssh-host> <amd64|arm64> [remote-dir]
```

`<ssh-host>` is anything `ssh` accepts (a `~/.ssh/config` alias, `user@host`); `<amd64|arm64>` is the server's CPU architecture; `remote-dir` defaults to `rwd-platform` in the ssh user's home directory. The script:

1. runs `make platform GOOS=linux GOARCH=<arch>` locally (SDK, console, gateway binary);
2. copies the Dockerfile, compose files and Caddyfiles, the demo pages and the binary to the server;
3. **on the first deploy only**, writes `.env` (mode 600) with a random owner password, `BIND`, `PORT` and the optional settings below, and prints the owner's login once. Later deploys never overwrite `.env`; they only append settings added in newer versions (such as `RWD_METRICS_TOKEN`) when missing;
4. if `data/rwd.db` exists, stops the gateway and copies the database to `data/rwd.db.bak-<YYYYmmddHHMMSS>` (schema migrations run on the next start), then fixes ownership of `data/` for uid 10001, using a throwaway container instead of sudo;
5. runs `docker compose up -d --build` and shows the service status.

First-deploy settings can be given as environment variables; they are only read when `.env` doesn't exist yet: `BIND`, `PORT`, `RWD_ADMIN_EMAIL`, `RWD_PUBLIC_URL`, `RWD_TRUSTED_PROXIES` and `RWD_DOMAIN`.

### Behind an existing TLS proxy

```bash
RWD_ADMIN_EMAIL=you@example.com RWD_PUBLIC_URL=https://rwd.example.com/v1 \
  deploy/platform/deploy.sh my-server amd64
```

Caddy is published on `127.0.0.1:18788`. Point your proxy at it and make sure the proxy:

- passes WebSocket upgrades (pages connect to `/v1/page`);
- doesn't buffer responses and allows long-lived connections: the console's live updates (`/v1/api/stream`) and MCP use streaming HTTP; the gateway sends a heartbeat every 25 seconds, so idle timeouts above 60 seconds are enough;
- sends `X-Forwarded-For`, `X-Forwarded-Proto: https` and the original `Host`.

For example, with nginx:

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    server_name rwd.example.com;
    # listen 443 ssl; ssl_certificate …; ssl_certificate_key …;

    location / {
        proxy_pass http://127.0.0.1:18788;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}
```

**`RWD_TRUSTED_PROXIES`.** Caddy passes the proxy's `X-Forwarded-*` headers on to the gateway only when the proxy connects from a trusted address. The default, `private_ranges`, covers a proxy on the same host or a private network. If your proxy connects from a public address (another server, a CDN or a cloud load balancer), set this to its ranges. Otherwise the gateway sees the proxy as the client: every request appears to come from the proxy's IP (which breaks API key IP allowlists and per-IP rate limits) and over plain HTTP (so the console cookie isn't marked `Secure`).

To publish Caddy on another address or port, set `BIND` and `PORT`.

### Direct HTTPS with `RWD_DOMAIN`

```bash
RWD_DOMAIN=rwd.example.com RWD_ADMIN_EMAIL=you@example.com \
  deploy/platform/deploy.sh my-server arm64
```

Before the first deploy, point the domain's DNS at the server and open ports 80 and 443 (TCP, plus UDP 443 for HTTP/3). With `RWD_DOMAIN` set, the first deploy writes `RWD_DOMAIN`, `COMPOSE_FILE=compose.yml:compose.tls.yml`, `BIND=0.0.0.0`, `PORT=80` and `RWD_PUBLIC_URL=https://rwd.example.com/v1` to `.env`. Caddy obtains and renews the certificate on its own (Let's Encrypt through Caddy's automatic HTTPS), keeps it in the `caddy-data` volume and redirects HTTP to HTTPS. Port 80 stays open for the ACME challenge and the redirect.

To switch an existing deployment to direct HTTPS, add those five lines to `.env` and run `docker compose up -d`.

## Deploying by hand

Without `deploy.sh`:

```bash
make -j16 GOOS=linux GOARCH=amd64                       # → gateway/bin/rwd-linux-amd64
# copy deploy/platform/* to the server, plus the binary as ./rwd
# on the server, in that directory:
mkdir -p data demo
printf 'RWD_ADMIN_PASSWORD=%s\n' "$(openssl rand -base64 12)" > .env && chmod 600 .env
docker run --rm -v "$PWD/data:/data" alpine:3.22 chown -R 10001 /data
docker compose up -d --build
```

### With the release image

Each gateway release also publishes the image `ghcr.io/zanel1u/remote-webview-debugger` for linux/amd64 and linux/arm64, tagged `<version>` (e.g. `0.2.0`), `<major>.<minor>` and `latest`, with the console and the SDK embedded. To run it instead of building one, replace the `build:` and `image:` lines of the gateway in `compose.yml` with `image: ghcr.io/zanel1u/remote-webview-debugger:<version>`, skip the binary, and start with `docker compose up -d`. Upgrade by changing the tag, then `docker compose pull && docker compose up -d` (back up `data/` first, as `deploy.sh` does).

For a quick try without Compose, the image also runs on its own: see the [quick start](../../README.md#1-run-the-gateway). On its own it does not trust `X-Forwarded-*`; if you put your own proxy in front, add `-e RWD_TRUST_PROXY=1`.

## Upgrading

Run `deploy.sh` again with the same host, architecture and directory. It rebuilds, copies the new binary, backs up the SQLite database and restarts the stack; `.env` is kept. Expect a short interruption. Pages reconnect by themselves: after a brief outage within seconds; after a longer one a page may first fall back to polling and return to the WebSocket within a few minutes, or as soon as an agent connects to it. Agents attached at that moment have to connect again.

## Backups

- **Automatic copies.** Each deploy copies `data/rwd.db` to `data/rwd.db.bak-<time>` before restarting. These accumulate; delete old ones from time to time.
- **Regular backups.** SQLite runs in WAL mode, so recent writes may sit in `rwd.db-wal` while the gateway runs. Back up a consistent copy by stopping the gateway briefly:

  ```bash
  docker compose stop gateway
  docker run --rm -v "$PWD/data:/data" alpine:3.22 cp -p /data/rwd.db "/data/rwd.db.bak-$(date +%Y%m%d%H%M%S)"
  docker compose start gateway
  ```

- **Restore.** Stop the gateway, replace `data/rwd.db` with the backup (and delete `rwd.db-wal` / `rwd.db-shm`), make sure it belongs to uid 10001, start the gateway.
- Back up `.env` as well. Database backups contain the API key pepper and the console session secret: store them privately.

## Postgres

Set `RWD_DATABASE_URL` in `.env`, for example `postgres://rwd:…@db.example.com:5432/rwd?sslmode=require`, and run `docker compose up -d`. The gateway container must be able to reach the database (a managed database, or a `postgres` service you add in a compose override file). The schema is created at startup; data is not copied over from an existing SQLite file. `deploy.sh` only backs up SQLite, so back Postgres up with `pg_dump` or your provider's snapshots.

## Day-to-day

```bash
docker compose ps                                     # status
docker compose logs -f gateway                        # gateway logs (the generated owner password, errors…)
curl https://rwd.example.com/v1/healthz               # {"ok":true,"version":"…","db":"sqlite"}
curl -H "Authorization: Bearer $RWD_METRICS_TOKEN" https://rwd.example.com/v1/metrics
```

- **Forgot the owner password:** change `RWD_ADMIN_PASSWORD` in `.env` and run `docker compose up -d`; it is applied on start.
- Run **one** gateway instance per database: live state (connected pages, control state) lives in the gateway process.
- The demo pages under `/demo/` are optional; delete `demo/` contents if you don't want them public (the next deploy copies them again).
